# Praxis 架构共识

本文记录已经确认的业务语义与架构约束，作为后续梳理和实现的依据，不表示现有代码已经满足这些约定。具体类型、目录、接口和同步机制按实际职责确定，不在业务边界尚未明确时预设实现。

## 一、背景与目标

Praxis 是本地运行、面向使用者本人使用的多 Agent 任务执行与协作桌面应用，技术形态为 Go、Wails 和 React。

应用围绕真实项目开展持续工作：用户通过主 Agent 提交任务，Agent 可以调用模型、读取和修改文件、执行工具，并通过子代理分工完成任务。系统保留可以浏览的执行历史，支持审批、停止和任务排队。

后端设计的目标是：

- 数据和运行资源的所有权明确。
- 长期身份、单次执行、历史事实与模型上下文各自承担清晰职责。
- 核心执行流程由直接调用编排，不依赖通知或观察者推进。
- 每项约束在明确的责任边界保证，其他层使用已经确定的结果。
- 不通过无意义的复制、重复校验和重复状态维护掩盖职责问题。

## 二、核心概念

| 概念 | 业务含义 |
| --- | --- |
| Project | 工作所依托的项目及其实际工作目录。 |
| Session | 组织同一项持续工作的配置、模型选择、任务队列和连续历史。 |
| Agent | 执行任务的主体身份及角色；主代理与子代理具有不同的上下文归属。 |
| Task | 等待执行的用户输入。 |
| Run | 推进一项任务的一次完整执行，从准备、运行到最终收尾。 |
| Turn | Run 内的一次 ReAct 迭代，包括普通模型请求及其触发的工具处理。 |
| ModelRequest | 一次实际模型调用，普通回答、风险审核和上下文摘要分别记录。 |
| Entry | 已经接纳的历史事实，例如用户输入、模型回答、工具回执和上下文摘要。 |

执行与历史按 Session、Run、Turn 和 Entry 组织。Agent 表达身份与角色，Task 表达待执行输入，ModelRequest 表达实际模型调用，不增加另一层会话或调度作用域。

主 Agent 的稳定身份可以跨多个 Run 持续存在，但不意味着模型一直在运行，也不要求所有执行资源长期驻留。

Run 结束后释放执行资源，其产生的历史仍可查询。Agent 身份、Run 运行实例和历史执行记录不能混为一个生命周期。

Run 的生命周期状态与结果分开表达。生命周期使用 `starting`、`running`、`ending` 和 `ended`；结果使用 `completed`、`yielded`、`failed` 和 `interrupted`。`interrupted` 表示用户主动打断，或应用异常关闭后恢复时对未完成执行的收敛；恢复原因与用户请求原因由独立的 FailureCode 区分。`yielded` 仅用于 Subagent 完成执行并主动向所属 Main Run 交付结果，不表示通用等待状态，也不用于替代 Main Run 的正常完成。

## 三、Session 与连续历史

### 3.1 会话是执行隔离范围

每个 Session 组织一条连续的主历史、一份当前模型选择和一个任务队列。Core Coordinator 按 Session 管理调度资源。

- 同一 Session 的普通任务按 FIFO 排队，同一时刻最多有一个活动 Main Run。
- Main Run 从准备阶段开始占用执行位置，必要收尾完成后才释放。
- 不同 Session 独立排队、独立执行，可以并行推进。
- 切换查看对象不停止后台 Session，也不清空其待办。
- 控制命令定位 Session 和具体 Run，不能用当前显示对象替换原目标。
- 子代理属于创建它的 Main Run，可以并行执行，不占用另一条 Main Run 调度位置。
- Task Queue 只存在于进程内，不作为持久化事实；清理、关闭 Session 或 `/reload` 时清理未领取的待办，不清理已经独立运行的 Run。
- Main Run 以 `completed` 正常结束且队列未暂停时，Coordinator 自动领取并启动下一项任务；主动 `interrupted` 不自动推进后续任务。

### 3.2 历史按追加顺序组织

Session 只有一条连续主历史，跨多个 Run 持续保留，每次执行在当前历史末尾追加 Entry。系统不建立 Branch 或其他并行历史树。Run 包含多个 Turn，Entry 记录消息、模型请求、工具结果、摘要和执行状态等具体事实。

- 同一日志内的顺序由追加位置确定，不为每条 Entry 保存通用父指针。
- 浏览较早的 Run、Turn 或历史页只改变展示范围，后续任务仍接续当前主历史。
- 子代理使用独立历史，不将中间模型交互直接追加到主历史。
- 上下文摘要调整后续请求选择的内容范围，原始记录保留。
- Entry 与通知分别设计；请求、调用、报告等标识由确有引用需要的具体 Payload 携带，存储归属由绑定的提交入口确定。

## 四、项目文件与成果

同一 Project 下的 Session 使用项目工作目录。不同任务的成果可以通过明确的文件名或目录保留，例如 `page-a.html`、`page-b.html`，由用户查看和继续修改。

会话历史记录执行事实；项目文件版本由实际文件管理方式决定。浏览历史、切换会话和停止 Run 不回滚、覆盖或合并已经产生的文件成果。同一项目中的并发文件操作可能互相影响，应在任务安排中明确输出位置。

## 五、Run、Turn 与模型请求

### 5.1 Run 与 Turn

Run 表示一次完整任务执行，可以包含多个 Turn。

一次 Turn 包括：

1. 普通模型请求及响应处理。
2. 模型提出工具调用时，完成相应的授权、审批和工具执行。
3. 接纳该轮实际产生的模型输出和工具回执。
4. 完成本轮处理，进入下一轮或结束本次 Run。

模型返回工具调用不表示该 Turn 已经结束；相关工具交互仍属于这一轮。单个 Turn 结束也不等于整个 Run 已结束。

### 5.2 模型请求独立记录

Turn 不等同于一次模型请求。

```text
Run
├── Turn 1
│   ├── 普通模型请求：提出工具调用
│   ├── 风险审核模型请求（需要时）
│   └── 工具执行与回执
├── 上下文压缩
│   └── 摘要模型请求（需要时）
└── Turn 2
    └── 普通模型请求：给出最终回答
```

上述过程可以包含两个 Turn 和四次模型请求。

- 风险审核关联触发它的 Turn，不单独占用一个 Turn；审核重试仍使用同一 TurnID。
- 摘要请求属于 Run；发生在两轮之间时不归入 Turn，允许没有 TurnID。
- 普通回答、审核和摘要的请求状态及用量分别记录。
- 一次模型请求首次尝试后最多重试三次，共最多四次尝试。每次尝试使用新的 RequestID 和独立计时，并将 `retryCount` 作为该 ModelRequest 的 Payload 保存：首次为 0，第一次重试为 1，依此类推，不从请求顺序推导。
- 未完成的 ModelRequest 在主动取消或异常关闭恢复时标记为 `interrupted`；Provider 错误达到重试上限时才作为失败结束。
- 用量按实际模型请求累计到所属 Run，不用 Turn 数量代替请求数量。
- 子 Run 单独累计自身用量，不把子 Run 的累计值再次算入父 Run。

具体身份字段和存储方式服从上述语义，不为 Turn 和 ModelRequest 分别建立重复的执行管理机制。

## 六、用户输入与模型选择

### 6.1 输入排队

本阶段仅支持普通任务排队，不实现 Steer。

- 执行中提交的新输入，进入目标 Session 的待办队列。
- 新输入用于后续 Run，不注入当前 Run。
- 不因为收到排队输入而立即打断正在进行的模型请求或工具执行。
- 队列只在内存中存在；主动暂停只阻止领取和启动，不阻止在允许的入口接纳输入。
- `/reload`、关闭 Session 或明确清理队列时，清理尚未领取的待办；已开始的 Run 不属于队列，不因队列清理而删除。
- 当前 Run 结束后，由调度流程决定下一项任务的启动；Main Run 正常 `completed` 且未暂停时自动启动下一项。

### 6.2 模型选择按 Session 独立

| 内容 | 归属 |
| --- | --- |
| 已加载的模型目录、Provider 凭据、工具启停和审批配置 | Session 的只读配置 |
| 当前选择的模型和推理等级 | Session |
| 本次执行实际使用的模型参数 | Run 开始时固定 |

Session A 可以使用模型 X，Session B 可以使用模型 Y。在 B 切换模型，不改变 A 的选择，也不改变已经开始的 Run。

配置编辑不应悄悄改变已打开会话或正在执行的任务；配置文件是模型目录、Provider 凭据、工具启停和审批默认值的唯一编辑来源。用户通过当前 Session 的 `/reload` 命令显式加载新配置。Reload 只允许在该 Session 没有活动 Run 时执行，期间禁止用户输入和新 Task 入队；目标 Session 取得新的只读内存快照，其他 Session 继续使用各自旧快照，已经冻结的 Run 不受影响。配置删除模型或更新凭据不改变尚未 Reload 的 Session，也不改变已冻结 Run。

## 七、主代理与子代理

- 主 Agent 持续接受任务，通过多个 Run 推进工作。
- 主 Agent 可以把明确的子任务交给 Subagent。
- Subagent 不允许递归创建 Subagent。
- 子代理使用自己的上下文和执行历史，不与主代理混用一份可变上下文。
- 子代理在创建时取得工具集合、工作目录和审批边界的权限快照；可以使用父 Run 的工作目录和已冻结配置，但不能发起人工审批、风险审核或请求额外权限。
- 子执行与父任务保持明确关联，父执行接收子任务结果。
- 子代理中间历史不直接混入主代理的模型上下文。
- 子代理完成后以 `yielded` 结果主动向绑定的 Main Run 交付结果；父 Run 通过明确的等待或收集工具将已交付报告接纳为后续模型输入，不按 Session 当前 Run 重新查找接收者。
- 子 Run 不设整体时限。`subagent_wait` 每次最多等待 30 秒，到期时返回普通工具结果 `timed_out`，尚未结束的子 Run 继续运行，父 Run 在下一轮决定后续操作。
- 父 Run 取消时立即取消其全部子 Run；子 Run 完整收尾前持续占用 Session 范围的并发名额。
- 每个 Session 最多 10 个活动子 Run，名额统计 Main Run 之外的全部子 Run，不建立额外的 Subagent 等待队列。
- 子执行资源释放后，执行记录和历史仍然可以查询。

## 八、数据与编排约束

### 8.1 三类数据分开

| 数据 | 职责 | 变化方式 |
| --- | --- | --- |
| 历史事实 | 记录已经发生的输入、回答、工具结果等 | Entry 接纳后内容只读 |
| 运行状态 | 表达当前执行进度、控制和等待 | 随所属执行推进 |
| 模型上下文 | 决定下一次请求携带哪些内容 | 选择和调整引用范围，不改写原始历史 |

三者可以共享只读内容，不各自维护需要相互同步和校验的可变正文。

历史按需读取。列表和状态展示使用必要的轻量信息，不要求打开会话时加载全部历史或全部已结束子代理的正文。

模型上下文是对历史的一种使用方式，不等同于界面历史，也不能受界面分页大小限制。上下文过长时可以在两次 ReAct Turn 之间压缩较早内容，但原始历史保留。摘要保存为一个正式 Entry；下一次压缩直接以最近摘要 Entry 加上其后的新增输入、模型输出和工具结果作为输入，不保存通用的原始 Entry 引用或额外上下文边界标记。摘要生成完成后即使 Run 被取消也完成保存，保存成功前不使用只存在内存中的摘要。

本次任务的输入由 Run 已接纳的用户输入事实确定。上下文选择需要定位或保留输入原文时，使用输入 Payload 的稳定消息标识及 Run 归属，不以对象地址、正文相等或当前切片位置判定身份。历史重新解码不改变输入身份；已选入请求的用户输入不再作为额外的 `userPrompt` 重复拼接。压缩范围与必要原文选择遵守同一上下文规则，不另存一套原始 Entry 引用。

### 8.2 核心流程直接调用

任务准入、模型调用、工具执行、历史接纳、Run 收尾和后续任务调度，都应有明确、可追踪的调用关系。

- 业务流程推进状态，事件描述已经确定的事实。
- 通知不负责保存 Entry、执行工具或领取下一项任务。
- 同一模型响应中的多个工具调用按 Provider 返回顺序登记。只读工具可以并行执行；会修改项目文件或其他外部状态的工具按 Provider 顺序串行执行。
- 工具结果通过所属 Run 和对应的 CallID 配对，并按 Provider 调用顺序组成一个工具结果调用块后追加到历史；工具完成顺序只影响实时通知，不改变历史顺序。
- Hook 提供显式扩展与观察，不暗中替代必要的业务步骤。工具参数在执行边界冻结后，Hook 只能观察、记录或阻止，不得修改参数。
- 没有观察者时，核心流程仍然正确。

### 8.3 所有权与保证

- 明确数据和资源由谁创建、持有、修改和释放。
- 外部输入在相应入口校验，内部使用已确定的类型和值。
- 同一项业务判断有明确负责人，其他层不重新审判已经接纳的内部事实。
- 只读内容可以共享；复制应服务于实际的修改隔离或生命周期需要。
- 同步机制对应真实并发访问，不通过重复加锁或重复状态维护替代清晰的编排。
- 模块拆分以实际职责为依据，不以增加接口、层级或目录为目标。
- 项目创建后工作目录路径不可变；不为多个 Session 共享 Project 增加自动文件锁或执行协调，文件冲突由用户和 Agent 任务安排负责。
- 工具输出的超大结果使用系统临时目录，不由 Project 或 Session 业务对象拥有长期生命周期；系统不承诺临时文件长期保留。
- FilePreview 不属于目标能力边界；文件访问由 Agent 工具完成，Wails 不暴露独立的文件预览入口。
- 工具已经产生的文件副作用不因历史保存失败而重放或回滚。
- Task、Run、Entry、事件和外部 API 不携带 BranchID，历史分页直接使用 Session 主历史和稳定 EntryID。
- Core 不依赖 Wails DTO。`wails/dto` 只定义外部输入、查询返回和事件载荷；`wails/bindings` 负责入口校验、调用 Core 或 Service，并将内部结果投影为 DTO。
- 内部 RunRecord、控制句柄、取消资源、凭据、内部配置和推理状态不得直接暴露；前端 API 负责 wire 类型转换和判别联合收窄。

### 8.4 工具交互的完整性

同一模型响应中的工具声明及其全部回执构成一次完整交互。下一次普通模型请求只能使用已经闭合的交互，不把少量已完成结果与仍缺回执的声明一起发给模型。

- 配对依据是 `(RunID, CallID)`；批量回执按 Provider 的声明顺序排列，不依赖工具完成顺序或仅判断相邻 Entry 的 Role。
- 每个声明都有对应回执，包括被拒绝、未执行、失败和中断的调用。已取得的可靠结果保留真实内容，缺少可靠结果的调用使用错误回执闭合。
- 正常中断由所属执行流程补齐回执；异常关闭后的缺口由会话加载实现按同一事实语义收尾，保存成功后才发布可用会话。恢复不重新执行原工具，也不覆盖已有结果。
- 压缩将整组交互作为历史资料摘要，或将整组保留在本次请求的原文范围内；不保留完整工具声明却只选择部分回执。完整性由执行、接纳及加载边界保证，内部消费方不重复维护另一套完成状态。
- 协议适配器只做合法编码。Anthropic 将全部对应结果放入紧跟工具声明的同一条 user 消息，工具结果在其他文本之前；相邻 user 内容按协议合并。其他协议保留各自的工具结果表达。

这里的完整性约束针对模型请求中的交互，不要求模型声明、外部工具副作用和全部结果跨步骤组成存储事务，也不增加恢复队列或自动重投机制。

### 8.5 上下文容量与工具结果预算

容量评估同时覆盖系统提示词、模型可见历史、工具定义、协议开销、输出预留及必要余量。接近窗口时的压缩阈值用于预警，不能替代发送前的容量判断。必要内容经过摘要和输出转存仍无法容纳时，明确返回容量错误。

输入 token 优先使用真实请求用量校准：在模型、Provider、协议、系统提示词、工具定义和已选历史前缀保持一致时，以最近一次成功普通请求的完整输入用量为锚点，只对新增模型可见内容做保守估算。锚点包含缓存读取和写入部分，不使用 Run 累计用量、摘要请求或风险审核请求的用量代替。

压缩替换历史、模型或请求配置变化、历史选择改变，以及有效用量缺失时，重新评估并建立可用锚点；不能直接沿用旧输入量。启发式系数用于缺少真实用量或增量内容的估算，不视为各类文本的精确 token 数或硬上界。

工具输出在成为 ToolResult 事实前受单项字节上限和整组上下文预算约束。多个单项合规的结果仍需共同装入下一次请求；预算根据当前模型窗口及已有必要内容确定，不仅依赖固定字符数。

超过内联预算的完整输出保存到系统临时文件，回执携带路径、大小和必要说明，Agent 可按需分段读取。所有调用仍保留对应回执，不为缩小请求丢弃某个 CallID；不通过截断结构化载荷制造无效结果。转存或保存失败明确记录错误及已发生的副作用，不重新执行工具以恢复输出。

### 8.6 模型请求前缀稳定性

摘要、历史及静态请求配置未变化时，后续请求沿既定顺序增加新的交互，保持已有系统提示词、工具定义和历史前缀的内容及编码稳定。工具定义使用确定顺序，调用标识映射保持稳定，内部时间戳和临时请求身份不混入对话正文。

动态容量数字等运行提示放在本次请求末尾，以协议允许的形式表达，不改写 SystemPrompt，也不作为历史事实或下一次摘要的输入。工具交互仍先完成全部结果，再附加运行提示。缓存复用服从上下文和协议的正确性，不能为了前缀不变保留悬空调用或过时内容。

## 九、风险与回退边界

- 共享项目目录意味着文件操作可能互相影响。成果需要通过不同文件或目录保留时，应在任务安排中明确。
- 历史浏览只读取事实，不恢复当时的项目文件或执行资源。
- 工具已经产生的真实结果不能因为迟到的取消信号被改写为“没有执行”。停止执行不等于撤销已经产生的文件或其他外部副作用。
- 应用重启后恢复历史和展示事实，对未完成执行进行必要收尾，不擅自重新请求模型、重新执行工具或继续旧任务。

## 十、后续实现的验证场景

以下用于核对后续实现是否满足共识，不表示已经完成验证：

1. Session A、B 可以同时执行，同一 Session 内的 Main Run 保持 FIFO 串行。
2. 查看 B 时，A 继续运行，A 的待办和控制目标不受页面选择影响。
3. A、B 可以分别选择不同模型和推理等级，已经开始的 Run 使用固定配置。
4. Run 执行中提交新输入，只进入对应 Session 队列，不改变当前 Run 的上下文。
5. 浏览过去的 Run 或 Turn 后提交任务，仍在当前主历史末尾开始新 Run。
6. Session 主历史和子代理历史按各自日志顺序读取，历史分页不混入当前流式内容。
7. 普通、审核和摘要请求分别记录用量；审核和摘要不被错误计为新的 ReAct Turn。
8. 主、子代理上下文分开，子执行结束后结果可交接，历史仍可查询。
9. Run 资源释放后仍能查询历史，重新打开应用不会自动重复执行已有工具操作。
10. 同一输入从历史重新解码后仍可按稳定消息标识定位；需要原文时能够选中，已选中的输入不重复追加。
11. 一轮多个工具的结果乱序完成、部分拒绝或中断后，下一次请求仍包含完整配对结果；Anthropic 编码为结果在前的单条 user 消息。
12. 单个或整组工具输出超过模型预算时转存完整内容，全部 CallID 仍有回执，分段读取保持结构化结果有效。
13. 相同前缀上的新增内容使用成功普通请求的真实输入用量校准；摘要、模型和配置变化后使旧锚点失效，缺少用量时使用回退估算。
14. 相同静态配置和摘要下的连续工具轮次保持前缀稳定；动态预算提醒不改写系统提示词或进入历史。
