# Praxis 架构共识

本文记录已经确认的业务语义与架构约束，作为后续梳理和实现的依据，不表示现有代码已经满足这些约定。具体类型、目录、接口和同步机制按实际职责确定，不在业务边界尚未明确时预设实现。

## 一、背景与目标

Praxis 是本地运行、面向使用者本人使用的多 Agent 任务执行与协作桌面应用，技术形态为 Go、Wails 和 React。

应用围绕真实项目开展持续工作：用户通过主 Agent 提交任务，Agent 可以调用模型、读取和修改文件、执行工具，并通过子代理分工完成任务。系统保留可以浏览和分叉的执行历史，支持审批、停止、任务排队以及不同尝试之间的效果对比。

后端设计的目标是：

- 数据和运行资源的所有权明确。
- 长期身份、单次执行、历史事实与模型上下文各自承担清晰职责。
- 核心执行流程由直接调用编排，不依赖通知或观察者推进。
- 每项约束在明确的责任边界保证，其他层使用已经确定的结果。
- 不通过无意义的复制、重复校验和重复状态维护掩盖职责问题。

## 二、核心概念

| 概念 | 业务含义 |
| --- | --- |
| Project | 工作所依托的项目及其实际工作目录。 |
| Session | 组织同一项持续工作的配置、分支和历史。 |
| Branch | 一条独立的尝试路线，保留自身的对话历史、模型选择、待办和执行归属。 |
| Agent | 执行任务的主体身份及角色；主代理与子代理具有不同的上下文归属。 |
| Task | 等待执行的用户输入。 |
| Run | 推进一项任务的一次完整执行，从准备、运行到最终收尾。 |
| Turn | Run 内的一次 ReAct 迭代，包括普通模型请求及其触发的工具处理。 |
| ModelRequest | 一次实际模型调用，普通回答、风险审核和上下文摘要分别记录。 |
| Entry | 已经接纳的历史事实，例如用户输入、模型回答、工具回执和上下文摘要。 |

主 Agent 的稳定身份可以跨多个 Run 持续存在，但不意味着模型一直在运行，也不要求所有执行资源长期驻留。

Run 结束后释放执行资源，其产生的历史仍可查询。Agent 身份、Run 运行实例和历史执行记录不能混为一个生命周期。

## 三、Session 与分支

### 3.1 分支的主要用途

分支用于从共同起点尝试不同路线，对比做出的不同效果，再选择满意的一条继续推进。

```text
共同历史节点
    ├── 分支 A：一种要求、模型 X → 效果 A → 后续调整
    └── 分支 B：另一种要求、模型 Y → 效果 B → 后续调整
```

一条分支可以经历多次任务和调整，不只是生成一次回答。选择某个分支表示沿着这条路线继续，不自动合并或删除其他分支。

### 3.2 并行执行与独立队列

同一个 Session 的不同分支允许同时执行。

- 同一分支的任务按 FIFO 排队，同一时刻最多有一个活动 Run。
- 不同分支独立排队、独立执行，不因另一个分支正在运行而失去执行资格。
- 队列属于分支的执行状态，不属于当前页面选择。
- 切换查看的分支，不停止其他分支的后台执行，也不清空其待办。
- 页面当前查看哪个分支，与哪些分支正在执行，是不同的状态。
- 控制命令应定位具体分支和目标 Run，不能以命令到达时的当前显示对象替换原目标。

```text
Session
├── 共享的会话配置与历史组织
├── 主 Agent 的稳定身份
├── 分支 A
│   ├── 模型选择
│   ├── 待办队列
│   └── 当前 Run A
└── 分支 B
    ├── 模型选择
    ├── 待办队列
    └── 当前 Run B
```

该结构表示业务归属，不要求机械地为每一层创建类型、服务或管理器。

### 3.3 从历史节点重新尝试

分支可以从之前的历史位置创建，不限定在当前末尾。

**分叉的最小粒度是 Turn，以完成该轮处理后的历史边界作为起点。** 不从模型增量、未完成的工具交互或任意单条中间记录切开。

```text
原分支：Turn 1 → Turn 2 → Turn 3 → Turn 4
                   └── 新分支：新的 Turn → 后续 Turn
```

- 从 Turn 2 的结束位置分叉，新分支继承截至该位置的历史，不把原分支后面的 Turn 3、Turn 4 带入上下文。
- 可以选择过去某个 Run 内的 Turn 边界，不要求分叉点一定是整个 Run 的末尾。
- 原分支及其后续历史保留，用于查看和对比。
- 共享祖先历史，不为创建分支复制已有正文。
- 新分支的后续任务形成新的 Run，不恢复旧 Run 的运行实例。
- 历史分叉不自动重放历史中的模型请求或工具操作。

## 四、项目文件与成果对比

分支隔离的是对话历史和执行路线，不是整个项目的文件版本。

同一 Project 下的尝试共享项目工作目录，可以通过不同文件或目录保留各自成果，例如：

```text
项目目录/
├── page-a.html
└── page-b.html
```

或：

```text
项目目录/
├── 方案 A/
└── 方案 B/
```

用户可以分别查看、运行和比较这些成果，再选择其中一份继续修改。

明确边界：

- 不因为分支功能引入项目文件快照。
- 不要求项目必须使用 Git，不以 Git 或 worktree 作为分支对比的前提。
- 切换分支不自动替换整个项目目录。
- 从历史 Turn 分叉，不自动把磁盘文件恢复到该 Turn 当时的状态。
- 不自动合并不同分支的文件成果。
- 不承诺分支之间的文件写入隔离；不同分支修改同一个文件时会相互影响。

保留不同成果与管理整个项目的文件版本是两项不同职责。Praxis 的这项分支能力不承担完整文件版本管理。

## 五、Run、Turn 与模型请求

### 5.1 Run 与 Turn

Run 表示一次完整任务执行，可以包含多个 Turn。

一次 Turn 包括：

1. 普通模型请求及响应处理。
2. 模型提出工具调用时，完成相应的授权、审批和工具执行。
3. 接纳该轮实际产生的模型输出和工具回执。
4. 完成本轮处理，进入下一轮或结束本次 Run。

模型返回工具调用不表示该 Turn 已经结束；相关工具交互仍属于这一轮。单个 Turn 结束也不等于整个 Run 已结束。

### 5.2 模型请求独立记录

Turn 不等同于一次模型请求。

```text
Run
├── Turn 1
│   ├── 普通模型请求：提出工具调用
│   ├── 风险审核模型请求（需要时）
│   └── 工具执行与回执
├── 上下文压缩
│   └── 摘要模型请求（需要时）
└── Turn 2
    └── 普通模型请求：给出最终回答
```

上述过程可以包含两个 Turn 和四次模型请求。

- 风险审核关联触发它的 Turn，不单独占用一个 Turn。
- 摘要请求属于 Run；发生在两轮之间时，不强行归入某个 Turn。
- 普通回答、审核和摘要的请求状态及用量分别记录。
- 用量按实际模型请求累计到所属 Run，不用 Turn 数量代替请求数量。
- 子 Run 单独累计自身用量，不把子 Run 的累计值再次算入父 Run。

具体身份字段和存储方式服从上述语义，不为 Turn 和 ModelRequest 分别建立重复的执行管理机制。

## 六、用户输入与模型选择

### 6.1 输入排队

本阶段仅支持普通任务排队，不实现 Steer。

- 执行中提交的新输入，进入目标分支的待办队列。
- 新输入用于后续 Run，不注入当前 Run。
- 不因为收到排队输入而立即打断正在进行的模型请求或工具执行。
- 当前 Run 结束后，由调度流程决定下一项任务的启动。

### 6.2 模型选择按分支独立

| 内容 | 归属 |
| --- | --- |
| 已加载的模型目录、Provider 凭据、工具启停和审批配置 | Session 的只读配置 |
| 当前选择的模型和推理等级 | Branch |
| 本次执行实际使用的模型参数 | Run 开始时固定 |

分支 A 可以使用模型 X，分支 B 可以使用模型 Y。在 B 切换模型，不改变 A 的选择，也不改变已经开始的 Run。

配置编辑不应悄悄改变已打开会话或正在执行的任务；会话通过显式重载更新配置。分支独立选择模型，不意味着为每个分支复制整份配置目录和凭据。

## 七、主代理与子代理

- 主 Agent 持续接受任务，通过多个 Run 推进工作。
- 主 Agent 可以把明确的子任务交给 Subagent。
- 子代理使用自己的上下文和执行历史，不与主代理混用一份可变上下文。
- 子执行与父任务保持明确关联，父执行接收子任务结果。
- 子代理中间历史不直接混入主代理的模型上下文。
- 子执行资源释放后，执行记录和历史仍然可以查询。

## 八、数据与编排约束

### 8.1 三类数据分开

| 数据 | 职责 | 变化方式 |
| --- | --- | --- |
| 历史事实 | 记录已经发生的输入、回答、工具结果等 | Entry 接纳后内容只读 |
| 运行状态 | 表达当前执行进度、控制和等待 | 随所属执行推进 |
| 模型上下文 | 决定下一次请求携带哪些内容 | 选择和调整引用范围，不改写原始历史 |

三者可以共享只读内容，不各自维护需要相互同步和校验的可变正文。

历史按需读取。列表和状态展示使用必要的轻量信息，不要求打开会话时加载全部分支及全部已结束子代理的正文。

模型上下文是对历史的一种使用方式，不等同于界面历史，也不能受界面分页大小限制。上下文过长时可以压缩较早内容，但原始历史保留。

### 8.2 核心流程直接调用

任务准入、模型调用、工具执行、历史接纳、Run 收尾和后续任务调度，都应有明确、可追踪的调用关系。

- 业务流程推进状态，事件描述已经确定的事实。
- 通知不负责保存 Entry、执行工具或领取下一项任务。
- Hook 提供显式扩展与观察，不暗中替代必要的业务步骤。
- 没有观察者时，核心流程仍然正确。

### 8.3 所有权与保证

- 明确数据和资源由谁创建、持有、修改和释放。
- 外部输入在相应入口校验，内部使用已确定的类型和值。
- 同一项业务判断有明确负责人，其他层不重新审判已经接纳的内部事实。
- 只读内容可以共享；复制应服务于实际的修改隔离或生命周期需要。
- 同步机制对应真实并发访问，不通过重复加锁或重复状态维护替代清晰的编排。
- 模块拆分以实际职责为依据，不以增加接口、层级或目录为目标。

## 九、风险与回退边界

- 共享项目目录意味着文件操作可能互相影响。成果需要通过不同文件或目录保留时，应在任务安排中明确，不能把历史分支误认为文件隔离。
- 从历史节点重新尝试只选择对应的对话历史，不承诺恢复当时的项目文件。
- 工具已经产生的真实结果不能因为迟到的取消信号被改写为“没有执行”。停止执行不等于撤销已经产生的文件或其他外部副作用。
- 应用重启后恢复历史和展示事实，对未完成执行进行必要收尾，不擅自重新请求模型、重新执行工具或继续旧任务。

## 十、后续实现的验证场景

以下用于核对后续实现是否满足共识，不表示已经完成验证：

1. 同一 Session 的分支 A、B 可以同时执行，同一分支内的任务保持串行。
2. 查看 B 时，A 继续运行，A 的待办和控制目标不受页面选择影响。
3. A、B 可以分别选择不同模型和推理等级，已经开始的 Run 使用固定配置。
4. Run 执行中提交新输入，只进入对应分支队列，不改变当前 Run 的上下文。
5. 从过去某个已完成 Turn 创建新分支，新分支只继承截至该轮结束的历史，原分支的后续历史保留。
6. 未完成的模型或工具交互不能作为分叉边界；分叉不要求等待到所选历史 Run 的最终末尾。
7. 不同尝试可以输出到不同文件或目录进行效果对比；切换和分叉不自动回滚、覆盖或合并项目文件。
8. 普通、审核和摘要请求分别记录用量；审核和摘要不被错误计为新的 ReAct Turn。
9. 主、子代理上下文分开，子执行结束后结果可交接，历史仍可查询。
10. Run 资源释放后仍能查询历史，重新打开应用不会自动重复执行已有工具操作。
