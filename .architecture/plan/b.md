# Session 无锁持有与命名分支方案

## 一、背景与目标

Praxis 使用 SessionID 标识一份持久化会话，该会话可以保存多条探索路径。SessionInfo 表达持久化元信息，Session 是每次打开后由页面独占的业务会话对象，持有选中的分支及已恢复的 Context。

设计同时解决以下需求：

1. 历史加载、执行恢复与正常运行具有明确边界，运行期间直接操作已经加载的内存 Entry。
2. 每次打开会话创建的 Session 对象由明确的所有者独占，不在每个历史或 Context 方法中重复查找对象、隐式加载和加锁。
3. 同一 SessionID 在不同页面打开时，各自拥有独立的 Session 对象和 Context，不混入另一个页面的后续对话。
4. 支持从当前位置尝试另一种方案、回到历史节点继续，以及保留被放弃的探索过程。
5. 提供稳定的命名分支和切换命令，恢复会话时不强制用户选择分支。
6. 工具执行事实保持不可覆盖，上下文加工只作用于对应模型请求的副本。

本方案不兼容旧历史，不提供自动迁移，也不自动删除真实用户数据。本文只描述目标设计及实施要求。

## 二、设计结论

### 2.1 已明确的产品规则

| 项目 | 规则 |
| --- | --- |
| 历史形态 | 一个 Session 的 JSONL 保存追加式历史树 |
| 树结构 | 历史追加记录使用 EntryID 和 ParentID 表达父子关系 |
| 创建分支 | `/branch [名称]` 从当前位置创建分支，并切换过去 |
| 切换分支 | `/switch` 打开选择器，`/switch <名称>` 切换到指定分支 |
| 历史导航 | `/tree` 查看树并选择历史位置 |
| 独立会话 | `/fork` 创建独立 Session，不等同于同文件内的分支 |
| 默认恢复 | 恢复最近有对话活动的分支，不在启动时强制弹出分支选择器 |
| 历史保留 | 不删除其他分支，不自动把其他分支合并进当前上下文 |
| 执行事实 | 已提交工具回执不允许 Hook 二次覆盖 |
| 业务会话 | 页面持有独立 Session 对象，不共享一个可变 Context，也不额外保存历史路径列表 |

### 2.2 需要落实的边界

- 分支隔离的是对话路径和模型上下文，不是文件系统或外部系统的副作用。
- 不同 SessionID 的会话不读取或修改彼此的历史。
- 是否存在并发取决于具体调用入口和对象所有权，不能仅凭“有多个 Session”就给每个对象增加锁。
- 内存态不天然等于线程安全；无锁的前提是可变对象没有并发访问者。
- 树结构不保证多个进程同时追加文件的正确性。
- 命名分支的指针与页面游标不同，不能让两个页面同时覆盖同一个命名分支的指针。

## 三、身份、数据与生命周期

### 3.1 业务身份与页面绑定

| 身份 | 含义 | 是否持久化 |
| --- | --- | --- |
| SessionID | 同一份对话历史容器 | 是 |
| BranchID | Session 内稳定的命名分支 | 是 |
| EntryID | 历史树上的一个确定节点 | 是 |
| BindingID | 接入层对页面此次打开会话的绑定标识，不属于 Session 业务身份 | 否 |

BindingID 由页面接入层或 Coordinator 管理，不使用操作系统窗口句柄。一个窗口可以包含多个页面；页面关闭后重新打开时取得新的绑定标识。Session 对象不保存该标识或页面事件订阅关系。

BranchID 不使用分支名称代替。名称用于展示和命令定位，BranchID 用于持久化归属、执行调度及事件过滤。

页面关闭后，BindingID 失效，分支和历史仍然存在。resume 恢复的是历史位置及分支，并创建新的 Session 对象，不恢复原页面或原执行协程。

### 3.2 持久化元信息 SessionInfo

SessionInfo 保存 SessionID、项目归属、标题、状态、审批设置等会话级元信息，并确定 JSONL 的位置。

SessionInfo 不保存 Context，也不保存所有页面共用的“当前分支”或“当前 leaf”。每个打开后的 Session 对象持有自己选中的 Branch 和 Context。

### 3.3 分支

分支至少包含以下语义字段：

| 字段 | 含义及约束 |
| --- | --- |
| ID | Session 内唯一、创建后不变 |
| Name | Session 内唯一的展示名称；去除首尾空白后非空 |
| BaseEntryID | 创建分支时选中的历史节点；空值表示历史树之前的起点 |
| HeadEntryID | 该分支最新提交的 Entry；创建时等于 BaseEntryID |
| BaseContextEventID | 可选，创建时继承的基础 Context 快照事件，固定后不跟随来源分支变化 |
| CreatedAt | 创建时间 |
| UpdatedAt | 创建或推进分支的时间，不由流式 token 更新 |

初始分支名称为 `main`。省略名称时，生成 `branch-<短标识>`，不使用窗口身份命名。

分支名称按规范化后的原文精确匹配。创建时重名返回冲突，不隐式复用已有分支。分支改名、删除和合并不属于本次范围。

### 3.4 Entry 与历史追加记录

历史存储的追加记录 `entryRecord` 保存 Entry 内容和树关系：

- Entry 的 `ID`：整个 SessionID 对应的历史内唯一，不能只在分支内唯一。
- `ParentID`：前一条路径节点的 ID，根节点为空。
- `BranchID`：本次追加推进哪个命名分支，创建后不变。
- Entry 的 `Sequence`：该 Entry 在物理日志中的事件位置，不用于判断祖先关系。

ParentID 和 BranchID 属于历史追加记录，不要求放进供模型上下文使用的 ContextEntry。重放时根据追加记录的 BranchID 推进对应 Head；BranchID 不用于过滤或收集该分支的全部上下文。

分支包含哪些 Entry 由 HeadEntryID 沿 ParentID 回溯确定，因此可以读到其他分支创建的共同祖先。这是明确继承，不是上下文污染。

工具调用身份继续由 ExecutionID 和 CallID 确定；不能仅凭 CallID 在整棵树中匹配回执。

### 3.5 业务会话 Session

Session 表示打开后的业务会话，由对应页面独占。打开时完成 Context 恢复，关闭时释放；切换分支时替换选中的 Branch 和 Context，不改变 SessionID。

Session 持有：

- SessionInfo。
- 当前 Branch，包括 BranchID 和已确认的 HeadEntryID。
- 当前分支的基础 Context。
- 当前 Execution 的归属、输入队列及绑定能力。

Session 不持有整棵历史树，也不另外保存所选路径的 Entry 列表或路径快照。打开、切换分支或从历史节点创建分支时，历史存储临时选择路径以恢复 Context；历史浏览则临时选择路径供页面展示。两者都不把路径作为 Session 的另一份状态保留。

Run 仍然只持有一次执行的 Agent、执行证据和临时状态。SessionInfo 表达持久化元信息，Branch 保存命名路径的位置，Session 持有本次打开后的业务状态，Run 持有一次执行状态；它们的生命周期不同。

## 四、历史树与命名分支

### 4.1 JSONL 的物理顺序不等于模型输入顺序

以下为 Entry 关系的简化示例，不是完整存储载荷：

```jsonl
{"id":"X","parent_id":null,"branch_id":"main-id","text":"共同输入"}
{"id":"A1","parent_id":"X","branch_id":"main-id","text":"方案 A"}
{"id":"B1","parent_id":"X","branch_id":"alternative-id","text":"方案 B"}
{"id":"A2","parent_id":"A1","branch_id":"main-id","text":"继续方案 A"}
```

物理追加顺序为 `X、A1、B1、A2`，逻辑关系为：

```text
X
├─ A1 → A2       main
└─ B1            alternative
```

选择 `main` 时，模型上下文来自 `X → A1 → A2`；选择 `alternative` 时，来自 `X → B1`。

不能按 Sequence 截取整个 Session 的连续区间作为分支历史，也不能把所有 Entry 按文件顺序直接拼成模型上下文。

### 4.2 创建分支与产生分叉不是同一时刻

创建分支时，两个命名分支可以暂时指向同一个节点：

```text
X → A1
     ↑ main
     ↑ alternative
```

在 `alternative` 追加消息之后才出现新的树节点：

```text
X → A1
     ├─ A2       main
     └─ B1       alternative
```

创建分支不复制共同历史，不复制正在运行的 Execution，也不触发模型请求。

### 4.3 分支指针与页面当前位置

- HeadEntryID 是分支持久化的最新位置。
- 页面当前位置通常等于 HeadEntryID。
- `/tree` 可以让页面查看更早的节点，但不直接回退命名分支的 HeadEntryID。
- 历史浏览位置由页面以 EntryID 表示，不要求 Session 保存路径列表，也不直接替换当前 Context。
- 从历史节点开启另一条路线时，先执行 `/branch`；普通输入不能静默覆盖已有命名分支的后续路径。

这使 `/switch main` 始终表示回到 main 的最新位置，而不是回到某个页面最后浏览的历史节点。

## 五、Session 对象不加锁的正确持有方式

### 5.1 所有权结构

```text
Coordinator
├─ 页面绑定与分支写入权
├─ 页面 A 绑定的 Session 对象
│  ├─ SessionInfo
│  ├─ 当前 Branch A 及其 Head
│  ├─ 已恢复的 Context
│  └─ 当前 Run
└─ 页面 B 绑定的 Session 对象
   ├─ SessionInfo
   ├─ 当前 Branch B 及其 Head
   ├─ 已恢复的 Context
   └─ 当前 Run

同一 SessionID 的历史存储
├─ 不可变 Entry、父子关系与分支事实
└─ 唯一日志追加入口：分配事件序号并串行追加完整记录
```

即使 SessionID 相同，页面 A 与页面 B 也不能持有同一个可变 Session 对象，不能共享 Context、可变 slice、map 或分支位置引用。

### 5.2 打开阶段完成加载与恢复

打开会话时明确执行：

1. 确认会话、项目和存储访问条件。
2. 取得该 JSONL 的进程内唯一日志资源。
3. 首次访问时完成日志重放、结构校验和中断恢复。
4. 确定恢复分支及安全的历史位置。
5. 取得该分支的页面写入权。
6. 按选中的 Head 临时选择历史路径，结合压缩快照恢复 Context，交给新建的 Session 对象；不保留另一份路径列表。
7. 在接入层登记 BindingID，绑定页面、Session 对象、执行能力及事件作用域。
8. 全部成功后才允许提交新输入和启动 Execution。

历史加载失败不发布半初始化实例，不允许后台执行先开始、再补加载 Context。

运行期间的 Context 读取、普通追加和压缩，不承担隐式加载或旧执行收尾职责。

### 5.3 运行阶段由一个所有者推进可变对象

- 一次执行由其执行协程顺序推进输入准入、模型请求、工具回执和 Context 替换。
- Session 空闲时，页面命令通过 Coordinator 的明确生命周期入口处理。
- 从空闲转为执行必须先完成所有权交接，不能在执行启动后继续由命令处理协程修改 Session。
- 运行中提交的新输入只进入已有输入队列，不直接修改当前 Context。
- Stop、Pause 等控制只发送取消或控制信号，由执行所有者完成回执及状态收尾。
- `/branch`、`/switch` 和改变当前位置的操作只在执行已收尾且没有待处理输入时进行。
- 前端运行期间消费事件并维护页面内存展示，不反复读取可变历史集合。
- 新页面由历史存储确认的记录恢复自己的 Context，不能读取另一个 Session 对象正在修改的 slice 或 map。

Session 内部普通方法因此可以保持直接调用，不需要自行加锁。不能把裸指针交给任意 Wails 请求或后台回调，再依赖调用方“自觉串行”。

耗时、用量及子执行结果若来自其他协程，不能直接修改所属 Session；它们通过明确的结果接纳入口或日志追加入口提交，父执行在约定边界接纳需要影响上下文的内容。

### 5.4 绑定能力，不在每一步重新定位 Session

Execution 开始时绑定已经准备好的 Session 对象及其当前分支能力。Loop 在本次执行期间直接使用这些绑定能力。

普通 Context 操作只使用该 Session 已准备的内存状态，不承担共享对象定位、历史加载或登记同步。正常流程为：

```text
打开会话并恢复 Context → 创建 Session 对象 → 绑定执行能力 → 顺序操作 Context
```

Session 对象关闭或切换分支时必须等待其执行完成收尾。绑定能力随执行结束或 Session 关闭而失效，不能被下一个页面或下一次打开复用。

### 5.5 无锁 Session 不等于所有资源都无同步

同一文件被不同分支追加，是多页面需求带来的真实共享资源访问，必须在日志拥有者处串行处理：

1. 分配下一个全局事件序号。
2. 填充事件及 Entry 的存储序号。
3. 编码并追加完整 JSONL 记录。
4. 返回提交结果。

该边界可使用文件粒度的短临界区，不覆盖模型请求、工具执行、Hook 或页面生命周期。Session 对象不持有这把锁，也不为 Context 的内存操作取得它。

会话业务层的历史存储持有历史树、事件序号及已提交事实的投影，用于为打开、切换和历史查询提供一致的记录。投影的发布与日志提交使用同一资源边界，不暴露正在追加的 map 或 slice，也不在这里保存页面的可变 Context。路径选择是恢复或查询时的临时计算，不作为 Session 字段；普通执行只读取所属 Session 的 Context。

该资源由会话业务服务登记并持有，Coordinator 按 PageID 登记页面使用期，PageID 与首次输入时创建的写入 BindingID 分离。仍有页面使用时复用历史存储，最后一个页面正常关闭且执行完成收尾后释放历史、配置和模型选择；再次打开重新恢复，不额外设计自动淘汰或后台刷新缓存。历史追加失败时保留首次错误，最后一个页面关闭返回 `session.unsaved_changes` 并保留内存，不自动重试可能部分成功的日志追加。非空的新会话在释放前退出空会话清理登记，退出清理不能依赖实例常驻判断是否为空。

写入期间不得回调 Session 对象或调用 Coordinator，避免锁反向依赖。提交成功后由调用方推进自己的内存状态。

Coordinator 的登记同步仅用于打开、关闭、分支写入权及执行交接等实际共享操作。不能据此给所有 Session 方法加锁，也不要求全局串行所有模型执行。

不新增通用 Actor 框架、异步业务事件总线或多层历史代理。复用既有调度入口和执行协程，保持核心调用可追踪。

## 六、多页面与分支写入权

### 6.1 一个命名分支只能有一个可写 Session 对象

不同分支可以同时执行，且共用历史中的不可变祖先。同一个命名分支不能同时被两个 Session 对象推进。

原因不是两个页面会互相读取 Context，而是它们都会更新同一个 HeadEntryID。仅复制 Context，不能解决这个持久化指针的归属问题。

分支写入权从页面绑定该分支开始，一直持续到切换或关闭完成，不仅覆盖模型正在运行的时间。它是 Coordinator 的内存生命周期状态，不写入历史，也不在每次追加时重新申请。

### 6.2 已占用分支的打开规则

本方案建议以下默认交互，实施前需确认：

- 默认 resume 或重新打开命中已被另一页面持有的分支时，从该分支最近一个已确认的安全节点创建自动命名分支，恢复独立 Context 并创建新的 Session 对象。
- 返回实际 BranchID、名称和分叉位置，页面明确显示“已独立继续”，不能静默声称仍在写原分支。
- 显式 `/switch <名称>` 命中已占用分支时返回冲突，不自动改成其他分支；用户可明确选择独立分支方式继续。

这样保留“打开同一 Session 可以独立使用”的目标，又不会让两个页面争用同一个命名指针。

若不采用自动创建，替代交互是打开时提示选择创建分支；不能退化为共享一个可变分支指针。

### 6.3 安全节点

可恢复或创建分支的节点必须是已经提交、能够形成合法模型历史的边界：

- 不包含尚未提交的流式文本。
- 不把尚未闭合的工具调用作为完整历史交给新执行。
- 工具调用和回执在所选路径中能够配对。
- 不继承另一个页面正在执行的协程、审批等待或待办队列。

若原分支正在产生工具调用，另一个页面使用其最近的安全边界，而不是任意取文件最后一行。

分支隔离不会撤销原分支已经执行的工具操作，也不阻止不同分支修改同一个项目文件。

## 七、命令与 resume 语义

### 7.1 命令契约

| 命令 | 输入与默认值 | 成功结果 | 主要失败情况 |
| --- | --- | --- | --- |
| `/branch [名称]` | 使用页面当前位置；省略名称则生成唯一名称 | 保存新分支并切换过去，释放原分支写入权 | 名称无效、重名、执行未收尾、有待处理输入、节点不安全、保存失败 |
| `/switch` | 无名称 | 展示本 Session 的分支选择器及占用状态 | Session 已关闭 |
| `/switch <名称>` | 按名称精确定位 | 切到该分支最新位置，建立独立基础 Context | 分支不存在、被占用、当前执行未收尾、有待处理输入、恢复失败 |
| `/tree` | 无参数 | 展示历史树，允许选择节点进行查看 | Session 已关闭；改变当前位置前必须完成当前执行收尾 |
| `/fork` | 使用当前位置 | 创建新 Session 和独立日志，建立初始分支 | 节点不安全、目标创建或保存失败 |

分支选择器展示名称、末尾消息摘要、最近对话活动时间及当前页面之外的占用状态。所有命令通过页面绑定定位对应 Session 对象，不能只带 SessionID。

本次不引入分支合并、自动合并摘要、分支删除或自动清理旧路径。

### 7.2 默认 resume

1. 选择 Session 文件或元数据记录。
2. 显式指定 BranchID 时使用该分支；否则恢复最近有对话活动的分支。
3. 对话活动由成功的 `entry.appended` 或 `branch.created` 确定，按提交顺序比较。
4. `usage.saved`、耗时、执行状态和 Context 快照等辅助事件，不改变默认恢复分支。
5. 没有对话时使用初始 `main`。
6. 应用分支占用规则，恢复 Context 并创建新的 Session 对象，不恢复旧执行。

因此，JSONL 最后一行不一定是恢复位置。默认恢复位置取目标分支的 HeadEntryID。

默认分支只在打开时选择。页面绑定完成后，追加记录始终使用该 Session 当前选中的 BranchID；其他页面产生的最近活动不能改变本页面的写入目标。

`/switch` 只改变当前页面绑定，不额外持久化“所有窗口共同的当前分支”。只浏览某个分支不改变默认恢复位置；创建分支或追加对话才改变最近活动分支。

### 7.3 最小使用示例

```text
打开 Session，使用 main
提交：实现登录功能
/branch 尝试另一种实现
提交：改用另一种 Token 刷新方式
/switch main
提交：继续原来的实现
```

两个分支共享分叉之前的 Entry，后续输入、回答和工具回执分别留在各自路径中。

## 八、持久化协议与提交边界

### 8.1 保留事件外壳，树关系属于 Entry

JSONL 继续使用事件外壳，保存 Sequence、事件身份、类型、对象键、创建时间及载荷。

不是每个事件都属于历史树。用量、耗时和执行记录不通过 ParentID 插入模型对话路径。

| 事件 | 作用 | 是否推进分支 Head |
| --- | --- | --- |
| `branch.created` | 保存分支身份、名称、分叉位置和继承的 Context 快照引用 | 初始化为 BaseEntryID |
| `entry.appended` | 在追加记录中保存不可变 Entry、ParentID 和推进目标 BranchID | 是 |
| `context.saved` | 保存对应分支的基础压缩结果及锚点 | 否 |
| 执行、用量、耗时等事件 | 保存明确归属的事实 | 否 |

### 8.2 追加 Entry 与推进 Head 使用同一个事实

`entry.appended` 本身就是分支推进事实，不为每条消息追加独立的 Head 更新事件。

提交前确认：

- Session 对象持有当前分支写入权。
- 追加记录中的 BranchID 与绑定分支一致。
- 追加记录中的 ParentID 等于当前分支已确认的 HeadEntryID。
- 非空 ParentID 指向本 Session 中已经存在的 Entry。
- 工具、Execution、Request 等归属与当前执行匹配。

日志追加成功后，历史存储接纳新的树节点，调用方只推进当前 Branch 的 Head 并更新基础 Context，不维护另一份历史路径。重放该事件时执行相同的分支推进，不依赖额外的窗口记录。

同一 EntryID 的重复提交先确认已保存事实：载荷一致则返回原提交结果，不一致则返回身份冲突；不能因为 Head 已推进就再次追加同一内容。

### 8.3 创建与切换分支的失败窗口

创建分支时，先准备名称、身份及基础 Context，再保存 `branch.created`；保存失败不改变当前页面绑定。

分支保存成功后才发布新的页面绑定并释放原分支写入权。若页面随后断开，新分支仍然存在，后续可以正常 resume，不依赖创建它的窗口。

分支创建使用明确请求身份，重复请求确认并返回同一个创建结果，不重复生成多个分支。

切换已有分支时，先准备目标快照并确认写入权，再替换页面绑定；失败保留原绑定。此过程不启动模型或工具，不把旧页面的队列转移过去。

### 8.4 写入失败与恢复

- 编码失败或写入前取消，不推进事件序号及运行态。
- 追加 I/O 错误可能已经产生部分写入，调用方不能据此自动重试工具或认为操作完全没有发生。
- 发生不确定追加结果后，阻断该日志后续提交，待重新打开并重放确认，避免继续使用过期事件序号。
- 日志恢复只修复不完整尾部；完整但不合法的记录明确报错，不静默跳过。
- 保持既有刷盘约定，不承诺每条记录或断电情况下的强持久化。

## 九、Context、压缩与 Hook

### 9.1 每个 Session 对象独占基础 Context

打开时由历史存储按所选分支的 Head 临时选择路径，结合该分支确认的压缩结果恢复 Context。恢复完成后，Session 只持有当前 Branch 和基础 Context，不保存历史路径列表或整个会话的最新消息列表。

日常执行直接使用已维护的内存 Context。追加时由当前 Head 确定 ParentID，提交成功后推进 Head 并更新 Context；压缩时替换基础 Context。切换分支或从历史节点创建分支时再恢复目标 Context，不在每轮模型请求前扫描整棵树。

`/tree` 和历史展示通过历史存储查询。前端初次打开或切换时取得展示用历史，之后使用带分支归属的事件维护内存展示；展示数据不要求 Session 再持有一份相同的路径列表。

### 9.2 压缩快照必须有路径锚点

`context.saved` 至少表达：

| 字段 | 含义 |
| --- | --- |
| BranchID | 产生该基础压缩结果的分支 |
| AnchorEntryID | 本次基础 Context 已覆盖到的路径节点 |
| Entries | 完整的基础压缩结果 |
| 事件身份 | 供分支创建时固定引用该快照 |

恢复时读取目标分支确认的快照，再追加 AnchorEntryID 之后、直到目标 Head 且包含 Head 的路径节点，即路径区间 `(AnchorEntryID, HeadEntryID]`。

不能使用“全局 Sequence 大于快照边界的所有 Entry”作为恢复规则，也不能使用整个 Session 最近一次 `context.saved` 覆盖其他分支。

摘要 Entry 的 Replaces 只允许引用本次路径中的合法历史范围。摘要本身作为正常 Entry 追加并推进所属分支 Head；快照保存不会额外推进 Head。

### 9.3 分叉时固定继承的压缩基线

创建分支时，可以引用来源路径已经确认的基础 Context 快照，但必须满足其锚点是 BaseEntryID 的祖先或 BaseEntryID 本身。

引用写进 `branch.created` 的 BaseContextEventID 后保持不变：

- 目标分支继承该快照及锚点之后到 BaseEntryID 的路径内容。
- 来源分支后续压缩不影响目标分支。
- 若选择的历史节点早于可用快照锚点，不引用该快照，直接从选中路径重建。
- 加载和切换不为补齐快照而调用模型；需要压缩时留给下一次正常执行。

不能仅以“快照锚点也是共同祖先”为由，采用另一个分支在分叉后新生成的快照。

### 9.4 工具事实与模型输入保持分离

工具执行顺序：

```text
工具执行及必要输出处理
    ↓
追加一次确定回执
    ↓
AfterToolExecution 只读通知
    ↓
继续执行
```

- AfterToolExecution 不返回修改后的 ToolResult。
- 通知错误按处理器汇总，由业务记录日志，不覆盖回执、不重试工具。
- 通知不提供可靠投递或跨崩溃补发承诺。
- 工具输出规范化、截断及不能持久化的信息处理，在保存及对外暴露之前完成，不依赖可选上下文 Hook。

模型输入顺序：

```text
当前分支的基础 Context
    ↓
compress 接收上下文 Entry 并进行原生压缩
    ↓
保存基础压缩结果
    ↓
复制为本次模型请求内容
    ↓
BeforeContextBuild 变换
    ↓
ContextBuilder 构建模型输入
    ↓
Provider
```

compress 不承担 Hook 变换职责。BeforeContextBuild 的输出不写回基础 Context、Session 历史或 Run 执行证据，每轮从基础副本重新加工。变换失败阻止本次模型请求，不回退发送未处理内容。

## 十、执行归属、队列与页面事件

### 10.1 调度单位

忙闲与队列必须区分 Session 内的不同分支：

- 同一分支一次只运行一个主 Execution。
- 不同分支可以独立执行。
- Task 入队时冻结 SessionID、BranchID 和提交身份，不能在稍后切换页面时改写任务归属。
- Execution、审批等待及子执行均保留所属 BranchID。
- 共享祖先中的 ExecutionID 只是历史归属，不表示新分支接管该执行。

AgentID 继续表达 Agent 身份，不兼任分支 ID。主 Agent 即使在不同分支中使用同一稳定身份，调度和查询也必须显式区分 BranchID 与 ExecutionID，不能只按 AgentID 判断忙闲。

### 10.2 事件路由

页面请求和执行事件需要明确携带或能够可靠解析：

```text
SessionID + BranchID + BindingID + ExecutionID
```

- SessionID 确定历史容器。
- BranchID 确定持久化路径归属。
- BindingID 由接入层确定此次页面绑定，隔离切换或关闭后的迟到事件，不作为 Session 的业务字段。
- ExecutionID 确定具体执行及其流式内容。

BindingID 不写进历史 Entry。当前执行归属一经确定，不随页面选择变化。

前端的消息、流式输出和乐观输入缓存不能仅按 SessionID 或主 AgentID 合并。页面只接纳匹配当前绑定的事件，不把另一分支的 Entry 追加到当前展示历史。

### 10.3 会话级查询

- 分支历史查询返回选中路径，不默认返回整棵树的平铺内容。
- 历史树查询用于显式浏览，不作为运行期间的轮询数据源。
- Session 总用量按实际执行记录汇总一次，不能因为共同祖先被多个分支引用而重复计费。
- 页面执行信息只显示当前分支及对应 Run。
- 标题、项目及审批默认设置仍为会话级配置；已冻结的执行配置不被后续修改追溯改变。

## 十一、恢复、关闭与多进程边界

### 11.1 重启恢复

同一 SessionID 的物理日志在没有已加载实例时统一恢复一次，再允许各页面按选中的分支恢复 Context 并创建自己的 Session 对象；仍有页面使用时不重复恢复，最后一个页面正常关闭后释放，再次打开重新恢复。

恢复检查包括：

- 事件序号及身份有效。
- EntryID 唯一，ParentID 指向此前存在的节点，不形成循环。
- BranchID 存在，分支名称唯一，Head 推进关系有效。
- 快照引用存在，锚点及内容属于可继承路径。
- 工具调用、回执和执行归属匹配，不跨兄弟路径配对。

旧进程未结束的 Execution 记为中断，缺失工具回执在原分支补齐。不重新执行工具，不恢复审批或模型请求，不为恢复创建 Run。

恢复回执只沿工具调用原分支的已确认 Head 追加，不插入既有节点之间，不重写 ParentID。若历史包含从未闭合工具链中间创建的分支，加载校验明确拒绝，不尝试自动修补其他分支。

本进程已有其他页面运行时，新页面打开只取得确认后的历史快照，不能把当前进程仍然活跃的 Execution 当作旧执行收尾。

### 11.2 关闭与删除

- 关闭页面先等待打开请求结束，再拒绝新输入，取消并等待当前执行完成收尾，释放分支写入权、页面登记和 Session 对象；纯浏览页面也要通知后端关闭。最后一个页面正常关闭时释放共享历史和配置，未保存数据导致关闭失败时保留页面和内存。
- 关闭一个页面不取消同一 Session 其他分支的执行。
- 未消费队列不转移到别的分支，按页面关闭策略明确取消。
- 删除持久化会话必须确认所有分支均无活动执行，并关闭相关 Session 对象和历史存储。
- 应用退出在所有执行及日志提交结束后再释放存储资源。
- 日志资源不在执行协程仍持有绑定能力时被提前释放。

### 11.3 多个 CLI 进程

桌面版本保持应用单实例约束，不实现多进程同时写入同一 JSONL。

若增加 CLI，目标策略是：同一 SessionID 在一个进程中可以对应多个独立分支的 Session 对象；不同进程不能同时写同一个会话日志。

CLI 应在打开日志到最后一个相关 Session 对象关闭之间持有跨进程的文件使用权。第二个进程明确返回会话占用信息；如需独立继续，创建新的会话文件，而不是绕过使用权共同追加。

跨进程使用权和进程内日志追加串行是两种边界，不能用 sync.Mutex 替代前者。CLI 能力及其锁实现不属于本次落地范围。

## 十二、实施范围与顺序

### 12.1 主要代码职责

| 位置 | 目标职责 |
| --- | --- |
| `backend/internal/core/session/` | SessionInfo、业务 Session、分支位置及命令规则；Session 独占 Context，不持有历史树或路径列表 |
| `backend/internal/core/session/entry/` | Entry 树关系与内容约束，保留不可变执行事实 |
| `backend/internal/service/session/` | 历史存储、明确的加载恢复、分支事实提交和 Session 准备，不在 Context 方法中懒加载 |
| `backend/internal/service/coordinator/` | Session 对象生命周期、页面绑定、分支写入权、执行调度与关闭交接 |
| `backend/internal/service/agent/execution/` | 绑定当前 Session 和分支能力，冻结执行归属 |
| `backend/internal/core/loop/` | 顺序执行、基础压缩编排和本次模型输入构建 |
| `backend/internal/infra/storage/` | 文件访问与完整记录追加资源，不负责选择业务分支或执行恢复决策 |
| Wails 绑定与前端会话页面 | 页面绑定、历史展示、分支命令、选择器和事件隔离 |

日志提交的业务序号分配与事实接纳由会话业务层负责；基础存储层不解释 Branch 或 Entry 载荷。资源拥有者处的串行约束不能扩散成各业务方法的重复加锁。

### 12.2 建议实施顺序

1. 明确 SessionInfo 与业务 Session 的职责、BranchID、追加记录的 ParentID 及命名分支记录；页面接入层管理 BindingID。
2. 实现树形日志重放、Head 推进及分支化 Context 快照恢复。
3. 收拢加载恢复阶段，建立页面独占的 Session、基础 Context 和绑定能力，不增加历史路径字段。
4. 建立分支写入权与文件粒度的统一追加边界，保证 Session 内存操作由单一所有者推进。
5. 将 Task、Execution、审批、子执行及查询归属扩展到分支。
6. 实现 `/branch`、`/switch`、`/tree` 及默认 resume。
7. 扩展页面绑定和事件过滤，验证多页面独立执行。
8. 同步现有架构说明和使用文档，不修改 AGENTS.md，不新增历史兼容链路。

`/fork` 可复用“导出所选路径、创建新 Session、重新建立初始分支”的能力单独实现，不阻塞同文件内分支能力落地。

## 十三、风险与回滚

| 风险 | 处理方式 |
| --- | --- |
| 仅删除锁却仍共享可变 Session 对象 | 先建立独占持有与生命周期交接，再移除锁；不以“内存态”代替串行保证 |
| Session 同时维护 Context 和历史路径副本 | 历史树归历史存储，路径只在恢复或查询时临时选择，Session 只维护当前分支位置和 Context |
| 两个页面推进同一命名分支 | 使用页面生命周期的单写入权，不只在模型运行期间限制 |
| 全局顺序误当路径关系 | 路径只按 ParentID 选择，Sequence 只用于物理日志完整性 |
| 来源分支的新压缩结果影响其他分支 | 创建时固定基础快照引用，后续快照按分支及锚点选择 |
| 打开新页面中断现有执行 | 无已加载实例时完成恢复，仍有页面使用期间的 attach 不重复收尾 |
| 切换后的迟到事件污染展示 | 按 BindingID、BranchID 和 ExecutionID 接纳事件 |
| 工具调用尚未闭合就分叉 | 只开放安全历史节点，不继承正在执行的工具链 |
| 分支被误认为工作目录快照 | 明确分支只隔离对话，不撤销或沙箱化外部副作用 |
| 不确定追加后继续写入 | 阻断该日志，重新打开确认，不自动重执行业务操作 |

发布前备份程序与数据目录。本方案不自动迁移旧日志，使用独立数据目录验证。需要回滚时同时恢复匹配的程序和数据备份，不让旧程序读取新协议日志。

实施前需确认的交互默认值包括：已占用分支默认 resume 是否自动创建分支、执行或队列未收尾时是否统一拒绝分支命令，以及 `/tree` 的历史位置是否要求显式 `/branch` 后才能继续输入。本文给出了明确推荐值；调整交互时仍须保留独占运行态、单分支单写入者和不可变历史规则。

## 十四、验证方式

遵守仓库约定，不新增或运行自动化测试，不启动开发服务，不使用真实用户数据进行协议验证。

### 14.1 构建与静态检查

后端变更后在 `backend/` 执行：

```sh
go build ./...
go vet ./...
go list ./...
```

Wails 服务签名变更后按仓库流程生成绑定，不手工修改生成文件；前端在 `frontend/` 执行 `npm run check`。

### 14.2 人工验收清单

在已有获授权运行的应用或人工启动环境中，使用独立数据目录验证：

1. 创建 Session 后存在 main，普通对话只推进 main。
2. `/branch` 创建时不复制共同历史、不请求模型，追加后才出现分叉。
3. `/switch main` 回到 main 最新位置，不带入其他分支的消息。
4. `/tree` 浏览历史不改写 Head；历史位置继续对话前明确创建分支。
5. resume 默认进入最近有对话活动的分支，耗时和用量事件不改变选择。
6. 同一 SessionID 打开两个页面后，按占用规则创建独立 Session 对象和页面绑定，事件和 Context 不串页，Session 不持有额外路径副本。
7. 不同分支可同时运行，日志序号连续，彼此不覆盖 Head。
8. 一个分支压缩后，另一个分支及共同原始历史不被改写。
9. 从压缩后的当前位置分叉，恢复继承基线；从更早节点分叉，不采用覆盖该节点之后的快照。
10. 工具执行过程中打开另一页面，不将现有执行记为中断，不继承未闭合工具调用。
11. 退出重启后，所有分支名称及 Head 可恢复；旧执行只收尾，不继续运行工具。
12. 后置工具 Hook 失败不改变回执；上下文 Hook 的文本变换不进入任何分支的持久化基础 Context。
13. 分支创建或切换失败时保留原页面绑定，重复创建请求不产生多个分支。
