# 会话、历史按需加载与用量管理方案

## 一、目标与边界

Praxis 采用单窗口工作区。前端按 SessionID 管理唯一会话页，后端按 Session 管理配置、主任务队列、连续历史和执行控制。

业务语义以 [architecture.md](../architecture.md) 为准，模块所有权和调用边界以 [code-style.md](../code-style.md) 为准。本文规定存储与按需读取的目标契约，不表示代码已完成。

基本约束：

1. 执行与历史按 Session、Run、Turn 和 Entry 组织；同一 Session 的 Main Run 串行，不同 Session 可以并行。
2. 主历史跨多个 Run 按追加顺序保留，子代理使用独立日志和上下文。
3. Entry 接纳后内容只读，不提供单条记录的独立删除入口。
4. SQLite 保存会话业务元数据；执行事实以 JSONL 为来源，历史定位、Run 展示和用量索引可由完整事实重建。
5. 正文按需分页，已结束子代理的历史在选择后加载，不要求全部正文常驻。
6. Run、Loop、当前展示页和未完整落盘的接纳结果按自身生命周期持有只读引用。
7. 模型请求独立记录用量，Run 累计自身请求，Session 累计唯一 Run，不重复计入子执行结果或查询快照。
8. Core 只提供唯一 AppendEntry 执行事实写入入口，记录与通知分别调用。
9. 会话加载成功即返回可用核心对象，读取、索引补齐和必要中断收尾由加载实现内部完成。

## 二、会话与前端工作区

### 2.1 唯一会话页

- 同一 SessionID 复用同一个会话页与固定作用域的 sessionStore。
- 会话页保存当前展示范围、Agent 选择、已加载历史、模型选择、草稿、错误和订阅。
- 切换标签或进入设置不销毁后台会话状态，输出、队列和用量继续接纳。
- 多个组件共享所属会话数据，不各自建立同一会话的页面使用期。
- 沿用现有状态管理能力，不额外建立页面引用计数或通用 Store 框架。

### 2.2 Core 加载入口

Core Coordinator 通过私有 sessionRegistry 定位已加载 Session。Service 调用 Core 的 LoadSession、GetSession 和 CloseSession，不保存另一份已打开会话集合。

- LoadSession 未命中时调用装配提供的 Repo 能力，取得可用对象后登记。
- Repo 加载内部完成必要索引补齐及中断收尾，不向 Service 暴露恢复步骤。
- GetSession 只查找已加载对象，不触发 I/O。
- 初始化只读取主历史当前展示所需的最新页，不展开全部已结束子代理正文。
- 后续查询按范围读取，不重新执行会话加载流程。
- 加载失败的对象不发布到 Registry。

### 2.3 关闭与删除

关闭会话通过 Coordinator 停止全部所属执行、清空待办并等待准备、工具、子执行和必要保存收尾，然后释放登记、文件和调度资源。前端成功后移除会话状态和订阅；失败时保留错误与必要操作入口。

关闭不删除会话业务元数据和历史，也不影响其他 Session。会话删除是明确的数据删除用例，在执行完整退出后处理，见第八节。

### 2.4 未加载、空内容与失败

- 未加载：尚未请求该 Agent 或展示范围的正文。
- 已加载为空：查询成功，范围内确实没有可展示记录。
- 加载失败：保留错误，不以空数组冒充成功。

不构造正文缺失的完整 Entry，不建立内部延迟加载代理对象。

## 三、Session、Run、Turn 与 Entry

### 3.1 归属与顺序

Session 主日志中的 Entry 按追加位置组成连续历史。多个 Main Run 依次追加，Turn 记录一次 ReAct 迭代的事实。子代理的独立日志关联所属子 Run，父 Run 只接收明确的报告或最终结果。

历史浏览固定读取范围，不改变下一次任务的上下文起点。新 Main Run 始终接续当前主历史。Run 结束前完成必要工具回执、子执行和终态保存，已结束 Run 不重新开始执行。

### 3.2 记录标识与存储定位

Entry 与前端 Event 分别定义。Entry 不要求所有 Payload 都具有统一 ID、RunID、TurnID 或 ParentID。

| 信息 | 位置与用途 |
| --- | --- |
| Session、所属 Run 和主／子历史归属 | 绑定提交入口及必要存储元数据，用于写入、恢复和查询 |
| Turn、模型请求、工具调用和报告等引用标识 | 需要它的具体 Payload，用于开始与结果配对、引用或消费 |
| 日志追加位置、完整记录偏移与长度 | 存储实现及派生索引，用于顺序、分页和定点读取 |
| 类型、时间、简短预览和必要关联 | 由事实生成的轻量查询索引 |

业务 Payload 不保存日志绝对路径或文件偏移。内部存储元数据只保留可恢复、可查询所必需的归属，不机械复制通知路由信封。

## 四、事实来源与物理存储

### 4.1 数据职责

| 数据 | 事实来源 | 查询方式 |
| --- | --- | --- |
| Session 身份、项目归属和标题等元数据 | SQLite | 直接查询元数据 |
| 主执行的消息、Run、Turn、请求和工具事实 | Session 主 JSONL | 按追加位置读取或派生轻量投影 |
| 子代理执行事实 | 所属独立 JSONL | 按明确子执行范围读取 |
| 正文位置、预览、Run 展示、请求用量与索引进度 | 从完整执行事实生成的 SQLite 索引 | 轻量查询，可重建 |
| 活跃执行、取消资源、临时输出与未落盘结果 | Core 对象及前端状态 | 按实际生命周期访问 |

SQLite 的会话业务元数据不能宣称全部由 JSONL 重建；备份包含匹配的数据库和日志。派生索引不成为第二份执行事实。

### 4.2 会话日志布局

以 `projects/<projectID>/sessions/<sessionID>/` 为根：

| 相对路径 | 内容 |
| --- | --- |
| `main.jsonl` | 连续主历史及所属 Main Run、Turn 和其他执行事实 |
| `subagents/<agentID>.jsonl` | 对应子代理的单次 Run 及其独立历史 |

日志只追加，不原地修改或删除其中某行。物理路径根据确定的项目、会话及历史归属构造，不加入业务 Payload。文件实现负责追加与位置读取，业务编解码负责解释具体事实。

## 五、轻量索引与正文按需读取

### 5.1 索引与正文分开

索引保存查询所需的类型、时间、Run 与适用 Turn 关联、短预览，以及日志位置。正文保存消息、思考、工具参数、真实回执、推理续传状态、摘要和请求结果等完整内容。

- 提交时使用已在内存中的事实生成短预览，不复制整段正文。
- Run 列表和 Agent 展示使用状态与结果投影，不展开全部历史。
- 未读取正文时只使用轻量元数据，不把缺失正文当成空消息。
- 正文定点读取与首次建立索引、增量补齐、必要恢复分别处理。

### 5.2 各操作的读取范围

| 操作 | 读取范围 |
| --- | --- |
| Session 列表、标题与项目导航 | 会话元数据 |
| 打开会话 | 必要恢复状态、运行展示信息和主历史最新页 |
| 浏览过去的 Run 或 Turn | 对应日志范围内当前页所需正文 |
| 向前翻页 | 固定范围内尚未加载的更早记录 |
| 列出 Agent 或 Run | 轻量身份、状态和结果投影 |
| 选择已结束子代理 | 该子代理当前页正文 |
| Session 累计用量 | 唯一 Run 的累计投影，不附带全量请求明细 |
| 构建模型上下文 | 摘要、明确保留内容和后续实际需要的正文 |

### 5.3 顺序与分页

分页按 Session 主日志或指定子执行日志定位，包含固定的读取上界、向前游标、页大小和是否还有更早内容。游标由存储读取边界表达，不要求为全部执行事实新增业务节点 ID。

先批量取得当前页的轻量定位，再读取正文，避免逐条往返。新增记录通过事件接纳，不能用不断变化的数组下标或偏移页码代替稳定游标。

分页合并按已有消息、请求等身份及明确读取范围处理，不重复返回同一记录。较早响应不能覆盖更新后的查询范围。

### 5.4 缓存与实时输出

- sessionStore 的作用域固定，页面切换不重置后台数据。
- 已结束子代理未被选择时，只保留其展示信息，不主动读取正文。
- 活跃子代理继续接收实时输出，结束后按明确展示策略释放临时缓冲。
- 当前展示页、活跃 Run、Loop 和未完整落盘记录各自持有必要引用。
- 历史浏览区域只显示固定范围的正文，不混入当前流式输出。
- 历史页与实时内容的接替、缓存保留和清理由明确动作处理，不在多个组件分散实现。

不引入 LRU、TTL、全局正文缓存或为缓存建立的记录引用计数。

### 5.5 模型上下文

界面历史、模型上下文和 Run 执行证据共享只读内容，各自选择需要的范围。

- 先通过轻量信息确定最后摘要、明确保留的原文和摘要后的内容，再读必要正文。
- 无摘要时读取实际需要的模型历史，不受界面页大小影响。
- Run 证据只保存本次实际接纳的只读引用。
- 执行元数据不直接作为对话正文交给模型。
- 内部推理续传状态按 Provider 契约投影，不直接发送到前端。

## 六、Run、Turn 与用量

### 6.1 模型请求独立记录

Turn 表示完整 ReAct 迭代，不等于一次实际模型请求。普通请求及其触发的风险审核关联同一 Turn，轮间摘要只关联 Run。

每次请求独立记录开始、成功、失败或取消。RequestID 配对请求事实与通知；失败或取消仍保留已经取得的真实用量和计时。未返回的用量表示未知，不当作已知零值，不按输出长度推算。

### 6.2 统计派生

- 用量只在具体请求事实保存一次，Turn 和 Run 的累计由它派生。
- 同一请求收尾只累计一次，不将开始和结束当作两次请求。
- Run 统计自身请求，子 Run 的累计不再次加入父 Run。
- Session 汇总唯一 Run，不重复叠加通知、查询快照或历史分页。
- 加载使用同一事实语义重建状态和统计，派生索引不是平行记录入口。
- Run 终态保存结果与必要关联，不重复持久化一套已经记录的累计事实。

### 6.3 查询

当前页请求明细按涉及的 Run、Turn 和 RequestID 范围批量查询，不为显示一页历史读取全会话明细。Session 总量独立读取必要的累计投影。

运行期最新投影与持久化投影按同一 Run 或请求替换，不相加。Run 累计与请求明细也不能再相加。资源释放后仍可通过事实和派生投影查询结果，不要求活动资源继续存活。

## 七、提交、索引与加载

### 7.1 唯一 AppendEntry

Loop 和 Run 统一调用绑定的 AppendEntry：

1. 在所属历史的同步提交边界确定存储归属、追加顺序和必要事实信息。
2. 接纳只读结果，向对应日志同步追加完整记录，取得偏移与长度。
3. 在 SQLite 事务中更新受影响的定位、请求、Run 和用量投影，以及该日志的连续索引进度。
4. 返回明确的接纳结果和错误；执行流程独立发布实际运行通知。

同一日志的追加顺序由明确的提交边界保证，不另建后台写入队列。普通追加不额外承诺断电持久化，不自动重试可能已部分写入的记录。

### 7.2 连续索引进度

- 索引变更和进度推进在同一事务中完成，不能跳过失败记录。
- 索引完整时不重新解码全部旧正文。
- 有未索引尾部时，从已完成位置继续；首次建立或明确重建时读取存活日志一次。
- 重建只处理明确属于存活 Session 的日志，不根据遗留目录重新发布会话。
- 普通正文读取只访问完整记录，不调用会备份或截断尾行的恢复逻辑。

### 7.3 提交失败

| 失败位置 | 语义与处理 |
| --- | --- |
| 日志追加失败 | 保留已接纳内存事实，明确错误并停止相关执行，不能认定完全未写入或自动重试工具 |
| 日志完整追加、索引失败 | 保留日志事实，从连续进度补齐索引，不重复追加业务记录 |
| 索引补齐失败 | 返回实际存储错误，不以陈旧投影冒充最新结果 |

未完整落盘结果不能随普通历史缓存释放。当前 Session 按同一事实合并内存与持久化投影，不能为内存结果伪造磁盘位置。记录完整落盘且索引可定位后释放仅为未落盘保留的引用。

记录与通知独立。运行结束通知不承诺日志保存成功，保存成功由提交结果确认。真实工具副作用不因日志失败重放。未落盘内容在关闭后仍可能丢失，不额外增加可靠投递或自动恢复队列。

### 7.4 可用对象加载

Repo 的 Session 加载实现内部：

1. 读取会话元数据和必要日志定位。
2. 补齐增量索引，按需重建派生数据。
3. 从请求与工具关联定位未结束或缺必要回执的候选 Run。
4. 只读取候选所需正文，按调用身份完成必要中断收尾。
5. 通过统一事实语义保存必要回执和 Run 中断结果。
6. 返回具备完整定位、读取和查询能力的核心 Session。

只有加载成功的对象登记到 Core Registry。Service 和 Coordinator 不显式组织以上步骤，也不逐条读历史组装对象。构造历史 Run 不启动执行。

加载不请求模型、不重新执行工具、不恢复旧审批等待或进程内待办。已经保存结果且无需收尾的正文不因此整体展开。

### 7.5 校验

外部身份和分页输入在入口校验，索引位置、元数据与完整载荷分别在读取边界校验。未访问正文的载荷校验延迟到实际读取；读取失败准确报告记录错误，不返回空内容或扫描其他日志掩盖错误。

## 八、会话删除与物理清理

删除由明确的会话用例调用 Core 完成停止和收尾，再提交会话及其全部派生数据删除。关闭与删除分别表达，不因切换页面删除数据。

- 逻辑删除以 SQLite 事务为提交点，事务失败不删除文件或发布成功状态。
- 提交后移除内存及前端引用，释放文件资源，清理对应 Session 目录。
- 删除范围包括主、子日志及所属索引，不读取全部正文才能确认范围。
- 物理清理失败时明确区分逻辑删除成功和清理失败，不重新发布已删除 Session。
- 重复清理只针对确定的目录，不存在按清理完成处理，不重复扣减用量。
- 未登记遗留目录不自动收养，不额外建立回收站、垃圾回收或删除状态机。

## 九、接口与前端接入

| 入口 | 目标职责 |
| --- | --- |
| LoadSession | Core 复用或加载可用 Session；应用层按需取得初始化展示数据 |
| GetSession | 定位已加载对象，不触发恢复 |
| CloseSession | 等待全部所属执行收尾，再释放登记和资源 |
| 历史分页查询 | 指定主／子历史及固定范围，向前读取一页正文 |
| Agent 与 Run 查询 | 读取轻量身份、状态与结果，不批量展开所有正文 |
| 请求用量明细 | 按当前展示涉及的请求范围批量查询 |
| Session 用量汇总 | 查询唯一 Run 的累计投影 |
| CancelTask | 按 SessionID 定位队列，只取消尚未领取输入 |

前端先订阅 `praxis:session:<sessionId>`，再取得初始化状态，保留加载期间的新变化。通知统一使用 kind、可选 runId 和 data；具体定位按事件需要提供，不另设完整路由信封。

sessionStore 固定作用域，Hook 组织请求和用户动作，纯函数接纳事件，组件负责展示。过期响应或旧 Run 通知不能覆盖新状态。对外只提供所需字段，不暴露冻结凭据、内部推理载荷、文件位置或活动控制资源。

## 十、同步、实施与验证

### 10.1 锁与资源

- Core Registry 的锁只保护查找、登记和移除，不覆盖加载、磁盘、模型、工具、Hook 或等待。
- 同一 Session 的入队、领取、准备期占用和完成交接在明确的并发边界内处理。
- 关闭、删除、历史读取和文件释放协调生命周期，不持续持有数据锁等待磁盘。
- 数据锁只保护共享容器和快照取得，遍历、排序和展示计算在锁外完成。
- 模型和工具执行期间不持续持有会话命令锁。
- 配置按只读引用替换，Run 锁和工具锁不覆盖跨对象存储或回调。
- SQLite 事务只处理必要元数据与索引，不执行长时间日志扫描或目录删除。
- 日志定位绑定资源生命周期，不为每次追加反查全部元数据或建立全局路径缓存。

### 10.2 实施顺序

1. 固定 Session 主历史、子执行日志、Entry Payload 和存储归属。
2. 落实 Core 加载与关闭入口、Repo 可用对象契约和唯一 Registry。
3. 接通 AppendEntry、完整记录位置、连续索引进度和定点读取。
4. 对齐 Run、Turn、模型请求事实及用量派生，保持正文按需读取。
5. 同步初始化、分页、Agent 选择、流式内容接替和前端订阅。
6. 核对关闭、删除、保存失败及必要中断收尾。

### 10.3 验证

实施时使用独立数据环境，核对：多会话并行及同会话 Main Run 串行；切换页面保留后台状态；分页无重复和遗漏；子代理历史按需读取；模型上下文不受界面页数影响；请求用量不重复累计；日志与索引失败不重放工具；加载只处理必要候选；关闭等待完整收尾；删除与物理清理失败分别表达。
