# 事件与前端接入：目标目录与实施清单

## 一、目标与边界

业务语义以 [architecture.md](../architecture.md) 为准，调用和类型所有权以 [code-style.md](../code-style.md) 为准。执行编排参见 [agent-structure.md](agent-structure.md)，本文件规定通知作用域、发布位置、Wails 适配和前端消费的实施目标，不表示代码已完成。

执行与历史按 Session、Run、Turn 和 Entry 组织。Coordinator 管理会话和调度，Run 的 Execute 直接调用 Loop。记录与通知分别调用，业务推进不依赖事件订阅者。

## 二、公共通知与会话作用域

### 2.1 业务事件

业务通知由可选 RunID 和具体 Payload 表达，kind 从 Payload 决定。队列、配置等会话级通知不要求 RunID。

| 信息 | 位置 |
| --- | --- |
| SessionID | 绑定的发布函数及前端订阅通道 |
| RunID | 运行内通知的共同定位信息 |
| TurnID | 迭代边界、按轮展示的流式输出等具体 Payload |
| RequestID | 模型请求状态与用量的具体 Payload |
| CallID | 工具调用、审批和真实回执的具体 Payload |
| Agent、父 Run 和父调用关联 | 初始化或创建通知中提供，后续按 RunID 定位 |

事件类型只引用公共数据，不读取 Run、Session 或业务服务，不通过 ID 查找运行对象。事件不是持久化 Entry，也不共用日志信封或编解码流程。

### 2.2 作用域绑定

Coordinator 取得绑定 SessionID 的发布函数。Run 再绑定本次 RunID，将同一通知能力交给 Loop。发布一次具体变化时，只提供所需 Payload，不反复拼装完整来源信息。

Wails 使用单个会话通道 `praxis:session:<sessionId>`，统一传递 kind、可选 runId 和 data。会话中的运行、工具、历史、队列和配置变化都通过这一作用域发送。

SessionID 保留在共享 Emitter 与 Wails 之间用于路由，不进入每个业务 Payload。函数绑定足以表达作用域，不为每个 Session 创建另一套 Emitter 或管理对象。

### 2.3 Emitter

- 应用只创建一份共享 Emitter。
- 同步分发，按已有订阅顺序调用，锁外执行回调。
- 不保存历史缓存、不重放、不查找业务对象。
- 不建立异步可靠队列、逐订阅者 goroutine 或跨执行的全局排序。
- 没有订阅者时，记录、工具执行、审批、Run 收尾和下一项任务调度仍然正确。

## 三、记录与通知分别调用

Run 和 Loop 将执行事实提交到唯一 AppendEntry，并在明确业务位置独立发布通知。AppendEntry 不隐式调用 Emitter，通知订阅者不提交业务事实。

| 流程 | 持久化事实 | 通知职责 |
| --- | --- | --- |
| Run 准备与开始 | 用户输入、固定配置所需事实及开始事实 | 当前执行身份、开始时间和实际状态 |
| Turn | 迭代开始与完成事实 | 本轮展示边界 |
| 模型请求 | 独立请求状态、已知用量与计时 | 等待、增量、结果和用量变化 |
| 工具调用 | 声明、授权所需事实及真实回执 | 审批入口、真实开始、进度和结果 |
| 摘要 | 摘要正文、保留引用及相关请求事实 | 必要的运行变化和用量 |
| 子执行 | 子 Run、报告、结果及父侧接收引用 | 身份登记、结果展示和资源释放 |
| Run 收尾 | 终态与结果 | 实际执行结束或中断，不表示持久化一定成功 |

完整模型内容形成 Entry 后保存，不逐 Token 写入日志。文本增量和工具进度可以直接通知。

工具真实结果不能因为通知失败或日志失败被改写或重放。保存错误明确上报并停止相关执行，不由事件层自动重试业务操作。

报告和最终结果先保存，再通过固定父 Run 的直接回调接收；父侧保存成功后交付或唤醒等待。这是业务交接，不通过 Emitter 实现。

## 四、事件消费语义

以下语义约束用于落实事件清单与具体字段，不将 Entry Payload 机械复制为通知类型。

| 通知内容 | 消费规则 |
| --- | --- |
| Run 开始 | 建立该 Run 的展示状态和身份关联，不清除较早执行结果 |
| Run 停止请求已接纳 | 显示停止中，不提前标记已中断或释放执行位置 |
| Run 终态 | 接纳实际结果，只清理该 Run 的临时运行信息 |
| Turn 开始与完成 | 只处理该 Run 下的本轮展示，不能推导整个 Run 完成 |
| 模型请求与用量 | 按 RequestID 归并普通、审核和摘要请求，不重复计数 |
| 工具审批与回执 | 按 RunID 和 CallID 配对，TurnID 只表达迭代归属 |
| 子执行创建 | 首次输出前提供身份、父 Run 和父调用关联 |
| 子执行释放 | 清理活动资源展示，保留结果与可查询历史 |
| TaskQueue 变化 | 更新所属 Session 的待办展示，不要求 RunID |
| 配置替换 | 更新目标 Session 的必要展示，不重载其他会话或改变已固定 Run 配置 |
| 展示错误 | 提供已由业务流程处理的错误，不替代执行终态 |

当前 Run 与最近结果可以有不同展示用途，但不为通知和列表建立重复可变执行实体。Wails 和前端只取得实际所需字段，不接收控制资源、凭据、完整配置或内部推理载荷。

## 五、Wails 适配

Wails 根据 Session 作用域选择通道，完成必要展示筛选后统一传输事件。种类与 Payload 的契约直接复用，不为每种通知逐个复制同形 DTO。

- 运行通知不包含页面写入绑定身份。
- Agent 关联在初始化或创建时给出，不要求所有通知重复提供。
- 时间与计时使用公共类型，Run 总耗时依据本次开始和结束时间。
- 审批详情沿用明确查询能力，不由通知携带全部内部工具上下文。
- 签名变化后按仓库流程重新生成绑定，不手工修改生成文件。

## 六、前端目录与状态

### 6.1 按语义组织目录

以下路径以 frontend/src 为根，文件数量按实际复杂度确定。

| 位置 | 职责 |
| --- | --- |
| api/events.ts | 类型化通知、会话通道及订阅函数 |
| api/sessions.ts、api/tasks.ts 等 | 按业务对象组织请求 |
| features/session/SessionPage.tsx | 装配代理、对话、任务和运行展示 |
| features/session/sessionStore.ts | 固定 Session 作用域的数据和变更通知 |
| features/session/applySessionEvent.ts | 纯函数接纳后端明确数据，不实现业务状态机 |
| features/session/useSessionData.ts | 会话加载、关闭、初始化和订阅资源 |
| features/agent/history/ | 按需分页、请求过期处理和历史合并 |
| features/agent/output/ | 文本、思考、工具和协作展示 |
| features/run/streaming.ts | 按 RunID 和 TurnID 合并及清理临时输出 |
| features/run/useRunControl.ts | 停止指定 Run 等请求 |
| features/task/TaskComposer.tsx、useTaskSubmission.ts | 任务编辑、提交、进行中与错误 |
| features/task/TaskQueue.tsx、useTaskQueue.ts | 待办展示及暂停、恢复、取消操作 |

普通任务提交与对子代理的补充指令按行为分别命名，不用一个宽泛 input 模块承载全部交互。会话作用域不要求把所有功能代码放入 session 目录。

### 6.2 sessionStore 的数据

| 数据 | 组织方式 |
| --- | --- |
| 会话信息 | 身份、模型选择及必要展示配置 |
| Agent 关联 | 身份、名称、顺序和关联 RunID |
| Run 展示 | 按 RunID 接纳状态与结果 |
| 流式缓冲 | 按 RunID、TurnID 保存临时输出，与普通数据分别订阅 |
| 已加载历史 | 按 Agent 或明确历史范围保存正文、分页、加载状态和错误 |
| 队列与共享选择 | 接纳后端待办及必要界面选择，不决定执行资格 |

Store 保存、读取和通知；事件函数应用明确信息；Hook 组织请求、用户动作和缓存策略；组件读取并展示。辅助模块可以是纯函数，不为每类数据再建立 Store 或订阅管理层。

选择 Agent、接纳分页、正式正文替换流式内容和释放缓存使用明确动作，不在多个入口分散维护。

### 6.3 运行与用量

- 当前 Run 状态以后端明确通知为依据，不从 TurnStarted 推导另一份 Agent 状态。
- 停止中与已中断分别表达，旧 Run 终态不能清理新 Run 输出。
- 聊天展示可以筛选普通迭代请求，统一接收入口仍接纳审核、摘要及其用量。
- RequestID 是请求归并键，不依赖 Turn 序号或文本长度。
- 后台会话的必要执行、队列和用量持续更新，正文按需读取。

## 七、初始化与异步边界

1. 为目标 Session 建立固定作用域 Store 和订阅。
2. 请求可用会话的当前完整展示状态及所需历史页。
3. 接纳初始响应时保留加载期间已经收到的新变化。
4. 后续事件与分页分别更新所属数据，不重新加载整页或全部 Agent。
5. 关闭成功后释放订阅和前端会话状态。

具体初始载荷、响应与通知的合并边界以及临时缓冲释放策略按实际语义收敛，不额外建立事件重放或可靠投递框架。过期响应不覆盖新查询结果，不把未加载正文解释为空内容。

## 八、后端发布位置与装配

后端路径以 backend/internal 为根。

| 位置 | 职责 |
| --- | --- |
| core/event | 公共通知数据、共享 Emitter 及 Session 函数绑定 |
| core/coordinator | 会话、队列及控制交接相关通知 |
| core/agent/run | 本次输入、Run 状态、结果及子执行关联通知 |
| core/loop | Turn、模型增量、请求状态和迭代展示通知 |
| core/toolexecution | 审批和真实工具执行通知 |
| core/entry、core/timing | 公共事实和计时类型，不反向依赖 Run 或 Loop |
| service/session | 配置等应用用例在结果确定后独立通知 |
| bootstrap | 创建一份 Emitter，将绑定能力提供给实际发布者 |

Run、Loop 和工具流程使用所需的窄发布能力，不为了发事件取得完整 Coordinator。Emitter 回调不推进调度、保存、授权或取消。

## 九、实施与验证

1. 固定 Session 通道、RunID 定位和具体 Payload 所需关联。
2. 对齐唯一 AppendEntry 与独立通知调用，公共类型不反向依赖执行对象。
3. 接通 Wails 的统一传输及必要字段筛选，生成绑定。
4. 前端按 Session 创建固定 Store，分别接纳普通数据、流式内容、队列、审批和用量。
5. 完成初始化合并、历史分页及正式正文接替临时输出的明确策略。
6. 核对旧请求、旧 Run 事件、关闭和保存失败场景。

人工回归重点：多会话隔离；同会话 Main Run 串行；连续 Run 结果不互相覆盖；多 Turn 输出正确归并；停止请求与终态分开；子执行结果关联正确；工具按 CallID 配对；审核和摘要用量不丢失；订阅关闭不阻止业务收尾；保存失败不重放工具。

代码实施按仓库流程执行后端构建、静态检查和前端 npm run check。只通过源类型生成绑定，不手工修改生成文件，不新增或运行自动化测试，不自动启动开发服务。程序、协议、前端和数据格式按匹配版本交付，持久化字段影响在对应实施中明确。
