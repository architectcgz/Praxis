# Praxis 代码实现约定

> **状态：代码风格与实现边界的讨论结果，作为后续实施依据。**
> 本文描述目标职责和编码约定，不表示相关代码已经完成。业务行为以 [current.md](current.md) 为准；本文中的候选类型名和目录位置需结合实际实现收敛，不要求逐项创建对应类型或文件。

## 1. 背景与目标

Praxis 的 Agent、Run、Turn、Branch、Task Queue 和 Subagent 已有业务架构共识。代码设计需要进一步明确：规则在哪里实现，状态由谁修改，执行资源由谁释放，以及各对象如何协作。

目标是让调用关系可以直接追踪，让状态和资源具有明确的所有者，同时控制抽象、类型数量和改动范围。

基本方向：

- Core 拥有领域规则和核心执行流程。
- Service 组织应用用例，协调核心对象与必要的外部能力。
- Coordinator 负责对象定位和少量跨对象生命周期协调。
- Branch、Run 各自的执行管理对象持有对应范围内的进程资源。
- Infrastructure 实现模型协议、文件系统、存储等具体技术能力。
- 类型名称表达实际职责；“运行时对象”作为分类术语，不作为统一命名模板。

## 2. 分层与调用方向

### 2.1 Core、Service 与 Infrastructure

| 位置 | 应承担的职责 | 责任边界 |
| --- | --- | --- |
| `core/session` | Session、Branch、历史关系、模型选择等领域模型及规则 | Branch 父子关系、删除约束、历史 Head 推进由核心对象维护 |
| `core/agent/run` | 单次执行的记录、状态、结果、执行证据和相关规则 | 不承担页面控制、后续 Task 调度或具体存储实现 |
| `core/loop` | ReAct 多 Turn 推进、模型请求、工具调用及执行输入边界 | 通过所需接口协作，不依赖完整 Service 或 Coordinator |
| `core/toolexecution` 等核心模块 | 工具授权、审批和执行控制的核心规则 | 具体文件操作、进程启动和外部协议由对应实现完成 |
| `service/agent/run` | 单次 Run 的准备、历史提交、Loop 协作与结算 | 调用核心规则，不自行实现另一套 Run 状态机 |
| `service/session` | Session / Branch 用例中的加载、保存和配置协作 | 不替代核心对象维护 Branch 规则 |
| Coordinator | 定位目标、路由命令、协调 Session 关闭等跨对象操作 | 不集中持有全部队列、执行状态、子代理与审批细节 |
| `repository` / `infra` | 存储契约及其实现、Provider、文件系统和具体工具 | 不决定 Task 调度、Run 完成条件或父子执行关系 |
| `bootstrap` | 创建共享依赖、选择实现并完成应用装配 | 不承载 Run 执行期间的业务决策 |
| `wails` | 外部请求、DTO、错误转换和前端通知适配 | 不复制核心规则和执行调度流程 |

Service 中允许存在应用编排逻辑。例如“准备 Run、提交输入、执行 Loop、保存结果”需要协调多个对象，可以由单次执行服务组织。状态转移规则、Branch 删除约束、队列行为应由相应核心对象实现，Service 调用这些行为完成用例。

### 2.2 对外入口与核心调用

外部控制应用的调用关系：

```text
Wails / API
  → 应用入口
  → 对应 Session / Branch / Run 的操作
  → 核心规则与执行流程
```

核心执行使用外部能力的调用关系：

```text
core/loop
  → Provider 接口 / ToolExecutor 接口 / 历史提交入口
  → 装配时提供的实现
  → 模型服务、工具或存储
```

“Agent 调用能力”在代码中主要表现为 Loop 和工具执行路径调用所需接口。Agent 身份对象不需要持有完整 Service 或 Coordinator。

必须区分源码依赖和运行时调用：核心通过接口或函数调用外层提供的实现是允许的；核心包不因此导入 `service` 或 `infra`。例如，Service 可以把历史提交方法绑定为 Loop 使用的函数。

接口只在确实存在的能力边界引入。内部对象之间可以直接使用具体类型，不要求所有调用都经过接口，也不为形式统一新增 `port`、`adapter` 或通用 `Capabilities` 层。

## 3. Session、Branch 与执行资源的所有权

### 3.1 Branch 属于 Core

Branch 的持久身份、祖先关系、历史 Head、Main Agent 身份和当前模型选择属于核心模型。Session 中涉及多个 Branch 的规则，由掌握这些关系的核心对象处理。

例如：

- 有子 Branch 的 Branch 不允许删除。
- 分叉复用祖先历史引用，并继承源 Branch 当前模型选择。
- 每个 Branch 拥有独立持久的 MainAgentID，不能从 SessionID 推导。
- Entry 接纳时，所属 Branch 的历史关系由历史拥有者更新。

Service 调用这些规则，并协调保存、配置加载和必要通知。不能由多个 Service 入口分别修改 Branch 集合、推导删除条件或推进历史 Head。

### 3.2 持久化数据与进程资源分别表达

| 内容 | 所有权 |
| --- | --- |
| Session / Branch 身份、分叉关系、历史引用 | 核心会话模型 |
| Branch 当前模型选择 | Branch 领域模型，按架构共识持久化 |
| Branch 已加载的只读配置引用 | Branch 的执行管理对象 |
| Task Queue、主动暂停、模型失效阻塞 | Branch 的执行管理对象；FIFO 行为由队列对象封装 |
| 当前 Main Run 的占用与调度 | Branch 的执行管理对象 |
| Run 状态、执行结果、时间和统计 | RunRecord 及其所属 Run |
| 单次执行的取消、完成信号、审批唤醒 | 该次活动执行对象 |
| 运行中输入、子代理结果接收和等待 | 所属 Run 的明确接收与控制边界 |
| Subagent 执行句柄与取消收尾 | 创建它们的具体父 Run |
| Subagent 并发名额 | Branch 范围内的执行管理，收尾完成后释放 |

区分持久化与运行状态，不等于必须各建一套同形模型。`context`、锁、channel 是资源和并发实现手段，不能仅凭使用这些类型就决定包归属；它们不进入持久化记录，具体放置位置由职责、生命周期和依赖方向决定。

队列与配置的生命周期不依赖前端当前显示哪个 Branch。切换 Branch 只改变视图，其他 Branch 继续执行。离开 Session 时，由 Session 级关闭流程协调其全部 Branch 收尾。

### 3.3 配置引用

Branch 保存已加载配置的只读引用；Run 启动时取得本次使用的配置引用，后续 Turn 保持稳定。Task 只保存待执行输入，不冻结另一份配置。

Reload 的用例流程由应用层协调：暂停目标 Branch 队列，停止并收尾目标 Branch 的活动执行，加载新配置，再替换该 Branch 的配置引用。模型选择失效与用户主动暂停分别表达。配置对象不原地修改，其他 Branch 保持原引用。

## 4. Coordinator 的规模与边界

Coordinator 是应用协调入口，不承担全局领域聚合的角色。

它可以保存定位对象所需的索引，但详细的可变状态由对应对象拥有。按 Session、Branch、Run 查找对象后，应调用对象提供的业务操作，而不是取出字段后在 Coordinator 内完成全部逻辑。

推荐职责分配：

- Coordinator：定位目标、接纳外部命令、协调跨对象关闭。
- Branch 执行管理：队列调度、当前 Main Run 槽位、配置引用和 Branch 级控制。
- 活动执行对象：一次执行的取消、等待、输入接收和子代理资源。
- 单次 Run 服务：准备、Loop 协作、历史提交和结算。
- 核心对象：业务规则、状态推进和领域事实。

Coordinator 中的运行数据限于定位和跨对象协调所需的引用；同一执行的可变状态、取消句柄和队列规则不应由多个对象分别维护。

拆分必须解决实际所有权问题。可以先在现有包内使用私有类型，再根据职责和依赖决定是否分包。不要求每层都建立 Registry、Manager 或 Service，也不为让 Coordinator 变短而添加纯转发层。

## 5. 命名约定

### 5.1 使用职责名称

“运行时对象”说明对象存在于进程中的生命周期，但不能充分说明职责。代码优先使用业务名称或职责名称，避免为 Session、Branch、Run 机械附加 `Runtime`。

以下是命名建议，不是必须同时建立的类型清单：

| 候选名称 | 适用职责 | 使用限制 |
| --- | --- | --- |
| `Session` / `Branch` | 会话与分支的领域模型 | 不因是否持久化而机械拆成多套同形对象 |
| `RunRecord` | 执行身份、状态、结果及统计等事实 | 不保存取消函数、channel 或执行回调 |
| `Run` | 一次执行的核心内存对象与执行证据 | 与 RunRecord 的分工明确，不维护第二份可变结果 |
| `TaskQueue` | FIFO 待办及领取行为 | 不表示 Run 的执行状态 |
| `SessionRegistry` | 已加载 Session 的定位索引 | 只在确有独立索引职责时使用 |
| `SessionBinding` | 外部调用与目标 Session / Branch 的绑定关系 | 不成为 Branch 队列和配置的生命周期拥有者 |
| `BranchExecution` | Branch 的队列、配置引用和活动 Main Run 管理 | 表示 Branch 执行管理，不表示某一次 Run；正式命名仍需核对调用语境 |
| `ActiveExecution` | 从准备占用到完整收尾的一次活动执行 | 适合需要覆盖 Run 尚未准备完成阶段的对象 |
| `RunExecution` | 已创建 Run 的执行资源与控制 | 与 ActiveExecution 按实际生命周期择一，不默认同时引入 |
| `RunHandle` | 外部只需停止、等待或定位执行时的窄句柄 | 不另持有一份执行状态；不强制设计为接口 |
| `ChildExecutions` | 父 Run 拥有的子执行集合及其收尾 | 集合复杂度需要封装时再抽取 |
| `SubagentQuota` | Branch 范围内的执行名额 | 简单计数可以留在拥有者内部，不额外建立全局服务 |

`SessionRegistry`、`SessionBinding` 与 Session 生命周期对象并不等价，不能仅为了去掉 `Runtime` 而互相替换。

`Controller` 适合控制入口，`Scheduler` 适合调度职责，`State` 适合状态值或投影，`Worker` 适合实际存在的工作执行者。名称不应暗示尚未采用的并发模型。

如果某类型确实表达一个完整且清晰的运行环境，`Runtime` 可以保留；不为替换后缀引入更模糊的名称。

### 5.2 业务术语一致

- `Task` 仅表示用户放入队列的待办，不用于命名 RunRecord、执行日志或执行结果。
- `Run` 表示一次完整 Loop，`Turn` 表示其中的一次模型调用及工具执行。
- 日志、变量、方法与事件使用同一身份语义。
- 不因新增类型而建立重复的 Status、Outcome、Reason 或 Failure 模型。
- 方法名表达业务动作；文件名表达职责，不按设计模式补齐空文件。

## 6. 状态推进、并发与取消

### 6.1 状态规则集中维护

Run 状态推进集中在 `core/agent/run` 的明确入口。应用层决定何时发起动作，核心状态入口维护合法转移和结果字段一致性。

```text
starting → running → ending → ended
starting / running / ending → interrupted
```

`ending` 只表示正常完成的收尾；`ended` 与 `interrupted` 都是终态。终态以后输入创建新 Run，队列暂停单独表达。

状态约束在拥有者入口判定，下层内部步骤使用已确定的前置条件，避免 Service、Run 和 Record 每层重复校验。是否返回错误应取决于该入口是否需要处理真实的状态冲突，不机械给每个内部赋值方法增加错误分支。

既有 Outcome 和 FailureCode 应结合上述状态语义收敛。保留的字段必须表达独立信息，不能要求多个字段分别维护同一个事实。

### 6.2 一个 Run 只有一个 Loop 执行者

模型请求、工具结果接纳、输入消费和后续 Turn 由同一 Run 的执行流程串行推进。这一约定约束 Loop 和执行状态的推进，不额外禁止工具或 Subagent 按其执行机制并行工作。

外部消息、子代理回调通过明确的接收入口提交数据和唤醒信号，不直接并发修改 Loop 上下文，不分别启动新的 Loop。

已接纳输入与执行完成使用同一个明确的并发边界：完成前处理已接纳的待交付指令，终结后拒绝对子代理继续输入。Main 的直接消息按当前 Run 是否还能接收，进入当前执行或后续新 Run，不能丢弃已接收输入。

输入用明确的业务类型表达，不建立承载全部业务的通用事件总线。是否共用一个输入结构，以实际消费和持久化语义为依据。

### 6.3 锁与资源靠近拥有者

- Coordinator 的索引锁只保护查找、登记和释放，不包住模型、工具、存储、Hook 或回调调用。
- Branch 的单 Main Run 占用从准备阶段开始，必要收尾完成后才释放。
- 同一 Branch 的检查与占用必须在同一并发边界内完成。
- Subagent 名额检查与预留原子完成；取消已接收不等于名额已经释放。
- `Locked` 后缀方法明确注明调用方应持有哪一把锁；不同锁的顺序必须清楚。
- 需要串行提交的历史写入由历史拥有者处理，不借用全局索引锁串行化全部 I/O。
- 外部停止命令定位明确的 RunID，不能在等待后改为停止 Branch 的另一条执行。

Context 用于取消、超时和请求范围，不承载业务状态。创建取消资源的执行管理流程负责取消和释放；完成信号必须覆盖必要收尾。子代理完成回调由外层执行流程发起，不依赖已经取消的子执行 Context。

## 7. 单次执行与 Subagent 协作

### 7.1 Main Run 的职责交接

```text
外部命令
  → 定位 Branch
  → Branch 接纳输入或预留执行槽位
  → Run 服务准备本次执行及初始历史
  → Loop 推进 Turn、模型和工具
  → 执行管理取消并收尾仍活动的子代理
  → Run 服务保存本次执行终态
  → Branch 释放占用并按队列状态决定下一项
```

单次 Run 服务不领取下一项 Task；Loop 不决定 Branch 队列调度；Coordinator 不逐条处理模型输出或维护 Turn 内部状态。

### 7.2 子代理归属与完成回调

Subagent 严格属于创建它的 Main Run。原生工具通过已绑定父 Run 的执行能力完成启动、等待、补充指令和取消；Loop 不需要获得完整 Coordinator。

子代理启动异步返回身份。子执行结束并完成必要收尾后，统一完成出口依次完成：

1. 保存子代理结束结果和历史。
2. 调用一次绑定父 Run 接收对象的完成回调。
3. 父 Run 接收并保存报告或结束信息。
4. 保存成功后唤醒等待或供后续上下文构建消费。

完成结果关联子执行身份、ParentRunID 和原始 ParentCallID。绑定父对象后，回调不再按 Branch 的“当前 Run”重新查找接收者。

父 Run 接收入口只提交结果和信号，模型推进仍由父执行路径完成。父 Run 收尾时保留必要结果并结束等待，不因通知再次调用模型。

并发限制按 Branch 计算，每个 Branch 最多 10 个子代理执行名额。子执行和取消收尾期间持续占用名额，不建立额外 Subagent 等待队列。

### 7.3 原生等待与授权

等待先读取已接收但未消费的报告和结束结果，再使用原生唤醒机制挂起。`any`、`all`、用户消息唤醒和父 Run 取消遵守架构共识，不使用轮询。

ReportID 用于正常新增报告消费，MessageID 用于补充指令接纳。等待结果引用已保存的报告，不重复复制报告正文。

委派参数在入口解析和校验一次。授权形成当前 Subagent Run 使用的稳定数据，同时约束 Provider 工具描述与真实工具执行。工具执行时的授权检查属于实际权限边界，不能因为入口校验过列表而省略。避免各模块分别复制权限判断规则。

## 8. 持久化、错误与通知

### 8.1 提交与通知

Entry 提交保留明确的同步结果和错误，核心执行能够知道是否保存成功。Session 确定历史关系，Run 使用已接纳的 Entry 引用记录执行证据。

持久化事实、内存已接纳结果和 UI 展示状态分别表达。写入失败不能显示为已成功保存，也不能因为内存还保留内容就继续正常执行。已经发生的文件修改或工具副作用不因日志失败重放。

报告和完成结果保存成功后才能作为新增输入交付或唤醒等待。核心提交、取消和调度不依赖可选 Hook 或 UI 事件订阅者。

子代理与父 Run 的两侧日志不构成原子事务。真实写入错误应明确上报并停止相关执行，不增加回调自动重投、恢复队列或可靠消息投递协议。

### 8.2 错误和重试

- 使用结构化错误和原因，按错误类型处理，不依赖错误字符串。
- 在负责业务语义的边界把错误映射为 Run 结果、前端 DTO 或日志；避免逐层复制同形错误模型。
- 模型请求首次失败后最多重试三次，每次失败和重试进度均保留并通知前端。
- 业务工具错误交给 Agent 决定后续动作，工具自身已有重试可保留。
- Subagent 停止不直接导致 Main Run 失败，是否重新委派由 Main Agent 决定。
- Coordinator 不自动重试整个 Run，不因为保存失败重放工具。
- 正常子代理最终回答直接复用；中断和超时只交付状态与原因，部分输出留在子代理历史。

### 8.3 前端边界

Wails 查询提供明确快照，事件携带定位所需的 SessionID、BranchID、AgentID、RunID 等身份。前端按所属对象合并增量，视图选择与后台 Branch 状态分开。

过期响应不能覆盖新的查询结果；后台 Branch 的有效事件仍更新其所属状态。前端不根据零散布尔事件重新实现后端 Run 状态机、队列调度或 Reload 规则。

DTO 表达传输和展示契约，不直接暴露完整内部运行对象。生成的 Wails 绑定通过工具重新生成，不手工修改。

## 9. 函数、类型和注释风格

- 主函数按正常业务顺序展开，校验、锁操作和复杂细节放在命名清楚的内部函数中。
- 只有复用、封装复杂逻辑或表达明确概念时才抽取函数；不为压缩行数增加转发层。
- 外部数据在相应入口校验，内部传递已确定类型的值，不反复检查同一输入。
- 运行中的状态变化和权限使用在拥有者边界处理，不与重复参数校验混为一谈。
- 类型归属于拥有其语义和生命周期的位置；正常跨模块引用无需通过复制模型消除。
- 配置按只读引用共享，短期执行数据不随意存入长期共享服务。
- 不为假设的罕见竞态增加复杂恢复体系；发现真实错误先修复产生错误的位置。
- 注释和项目文档使用中文，Praxis 自身错误信息遵守后端约定使用英文。
- 注释解释并发前提、生命周期、失败后状态等不明显约束，不重复代码字面含义。
- Go 复合字面量的多字段换行、React 写法和生成文件处理遵守各目录 AGENTS.md。

## 10. 实施收敛、风险与验证

### 10.1 实施顺序

1. 根据真实调用梳理每个字段、规则和资源的拥有者。
2. 将领域规则集中到核心对象，将单次 Run 流程集中到执行服务。
3. 让 Branch 执行管理和活动执行对象分别持有自己的资源，收敛 Coordinator 职责。
4. 明确完成回调、输入接纳、历史提交和队列调度的直接调用关系。
5. 按实际职责选择类型名，再决定是否需要移动文件或拆包。

`BranchExecution`、`ActiveExecution` 等是目前的候选名称。是否保留既有 `activeRun`、是否需要独立句柄和子执行集合、这些类型放在哪个包，在实施时依据最终职责确定。候选类型不作为创建完整对象层级的要求。

### 10.2 风险与回滚边界

主要风险是拆分后出现重复状态、取消链路断开、回调投递给错误 Run，或绑定切换导致 Branch 资源提前释放。通过明确单一所有者、固定父 Run 接收对象和完整收尾边界控制这些问题。

按职责小步修改，避免同时重命名全部目录和改写整个执行流程。代码回滚以独立变更为单位，不通过重放已产生副作用的任务恢复状态。涉及持久化格式的实施需说明格式影响；不额外承诺旧数据迁移或旧执行自动恢复。

### 10.3 验证方式

文档核对以 current.md 的业务边界、类型所有权和命名一致性为主。

后续代码实施遵守仓库验证流程：

- 后端在 `backend/` 执行 `go build ./...`、`go vet ./...`、`go list ./...`。
- 修改 Wails 签名后重新生成绑定，并在前端执行 `npm run check`。
- 不新增或运行自动化测试；需要数据验证时使用独立临时目录，不使用真实用户数据。
- 不自动启动开发服务；人工回归使用已有服务，必要的新服务启动按仓库授权规则处理。
- 重点核对 Branch 并行执行、停止后新 Run、队列独立暂停、Reload 隔离、子代理完成回调及 Session 全部 Branch 收尾。
