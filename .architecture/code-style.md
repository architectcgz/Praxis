# Praxis 代码实现约定

> **状态：代码风格与实现边界的讨论结果，作为后续实施依据。**
> 本文描述目标职责和编码约定，不表示相关代码已经完成。业务行为以 [architecture.md](architecture.md) 为准，实施核对与待办参见 [current.md](current.md)。目录和类型围绕明确职责组织，不要求为每项职责创建独立类型或文件。

## 1. 背景与目标

Praxis 的执行与历史按 Session、Run、Turn 和 Entry 组织，Task Queue 和 Subagent 围绕这套归属协作。代码设计需要进一步明确：规则在哪里实现，状态由谁修改，执行资源由谁释放，以及各对象如何协作。

目标是让调用关系可以直接追踪，让状态和资源具有明确的所有者，同时控制抽象、类型数量和改动范围。

基本方向：

- Core 拥有领域规则、核心执行流程，以及相应的进程内状态和控制资源。
- Coordinator 位于 `core/coordinator`，统一协调已加载会话的管理、输入路由、Session 队列与活动 Run 的交接。
- Session 组织连续主历史、模型选择和会话规则；队列与 Main Run 占用按 Session 隔离，由 Coordinator 管理调度。
- TaskQueue 封装队列行为，Run 统一拥有单次执行的信息和行为，并通过 `Execute` 直接调用 Loop；活动 Run 控制对象持有取消与完成等资源。
- Entry、模型请求等共享事实类型位于 Core 公共模块，Run、Loop、Session 使用同一套记录类型。
- Service 组织应用用例、配置协作和必要保存，通过 Core 的公开入口取得会话及控制执行。
- Infrastructure 实现模型协议、文件系统、存储等具体技术能力。
- 类型名称表达实际职责；“运行时对象”作为分类术语，不作为统一命名模板。

## 2. 分层与调用方向

### 2.1 Core、Service 与 Infrastructure

| 位置 | 应承担的职责 | 责任边界 |
| --- | --- | --- |
| `core/session` | Session、连续历史、模型选择等领域模型及规则 | 历史归属、读取范围和会话规则由核心对象维护；每个 Session 只有一条主历史，不建立 Branch |
| `core/task` | Task 数据，以及 FIFO、领取、暂停和恢复等队列行为 | Task 不保存执行配置；队列只存在内存，不推进 Run 状态或自行启动执行 |
| `core/coordinator` | 会话加载与定位、输入路由、按 Session 隔离的队列调度、活动 Run 登记及控制交接 | 调用队列和 Run 的明确行为，不复制其状态规则，不展开模型、工具和存储实现细节 |
| `core/entry` | Entry、内容块、Turn 和模型请求等共享事实类型 | 只表达事实数据和身份关联，不引用 Run、Loop 或 Session 执行对象；不携带 BranchID |
| `core/timing` | 通用计时记录与测量能力 | 供模型、工具和执行流程共享，不依附于 Run 模块 |
| `core/event` | 公共通知数据、订阅分发及作用域绑定 | 不反向引用 Run 等执行对象，不承担事实持久化或业务推进 |
| `core/agent/run` | 单次执行的身份、配置、状态、结果、统计、执行证据和完整执行入口 | Run 自身提供 `Execute`，组织准备、Loop 调用和收尾；不领取下一项 Task |
| `core/loop` | ReAct 多 Turn 推进、模型请求、工具调用及执行输入边界 | 通过所需接口协作，不依赖完整 Service 或 Coordinator |
| `core/context` | 模型上下文选择、容量估算和压缩规则 | 从已接纳历史选择模型可见内容；负责压缩准入，不修改原始历史，不执行 Provider 重试 |
| `core/provider` | Provider 中立的模型请求、流事件和停止语义 | 只表达一次请求尝试及其统一结果，不包含协议编码、工具执行或 Run 调度 |
| `core/toolexecution` 等核心模块 | 工具授权、审批和执行控制的核心规则 | 具体文件操作、进程启动和外部协议由对应实现完成 |
| `infra/providers` | 具体模型协议的请求编码、响应解码和流式资源管理 | 将协议细节转换为 Provider 中立事件；管理 HTTP 响应体和解码资源，不自行重试或压缩 |
| `service/session` | Session 应用用例、配置协作和必要保存 | 通过 Core 入口取得会话，不持有会话注册表，不显式组织内部恢复，不替代核心会话规则 |
| `repository` / `infra` | 存储契约及其实现、Provider、文件系统和具体工具 | Session 加载成功后返回可用对象；不决定 Task 调度、Run 完成条件或父子执行关系 |
| `bootstrap` | 创建共享依赖、选择实现并完成应用装配 | 将 Repo 加载、Provider、工具、事实提交和通知能力提供给 Core，不承载执行期间的业务决策 |
| `wails` | 外部请求、已有接口返回、错误转换和前端通知适配 | 使用独立 DTO 完成输入校验和展示投影，不暴露内部 Run、凭据或控制资源，不复制核心规则和执行调度流程 |

分层依据是实际职责。同一 Session 内的 Main Run 串行执行、输入排队和正常结束后的任务交接属于 Core 的执行规则；配置加载、应用用例中的外部能力协作可以由 Service 组织。状态转移、会话历史和队列行为仍由各自核心对象维护。

### 2.2 对外入口与核心调用

| 调用场景 | 入口与业务调用 |
| --- | --- |
| 加载、定位或关闭 Session | Service 调用 Core Coordinator 的会话入口 |
| 提交消息、Task 排队及执行控制 | 应用入口调用 Core Coordinator，再由其协调队列与 Run |
| 会话创建、删除、查询和列表 | Session 应用服务协调保存，涉及已加载对象时通过 Core 入口取得会话 |
| Session 实际加载 | Core Coordinator 调用装配时提供的 Repo 加载能力，取得可用 Session 后登记 |
| 单次 Run 的准备和执行 | Core Coordinator 从 Task 创建 Run 并提供本次依赖，调用 Run 的 `Execute` |
| ReAct 执行 | Run 的 `Execute` 直接调用 Loop，Loop 在各轮请求前调用 ContextBuilder |
| 模型和工具调用 | Loop 和单次执行流程调用所需接口或函数，由装配时提供的实现完成 |
| Provider 流式请求 | Loop 发起一次 Provider 尝试并消费统一事件；重试、请求事实和 Run 结果由 Core 执行流程处理 |
| 执行事实提交 | Loop 和 Run 统一调用绑定的 `AppendEntry`，由存储实现完成 JSONL 写入 |

Coordinator 的公开入口表达业务动作，例如 `SubmitMessage`、`EnqueueTask`、`StopRun`、`PauseQueue`、`ResumeQueue` 及必要查询。Main 的普通任务输入遵守架构文档确定的排队规则，执行中提交的输入用于后续 Run。调度检查、位置预留和完成交接保留为内部方法。

“Agent 调用能力”在代码中主要表现为 Loop 和工具执行路径调用所需接口。Agent 身份对象不需要持有完整 Service 或 Coordinator。

Core 内的依赖方向是 Run 调用 Loop，Run、Loop 和 Session 共同使用 `core/entry` 等公共数据类型。Loop 及其共享能力不反向依赖 Run 的执行对象；共享请求记录、状态数据和计时类型按其公共语义归属。

必须区分源码依赖和运行时调用：Core 可以通过接口或函数调用外层提供的实现，但不导入 `service` 或 `infra`。Repo 加载、历史提交等外部能力在 `bootstrap` 中绑定后提供给 Core；Run 与 Loop 使用明确的直接调用。

接口只在确实存在的能力边界引入。内部对象之间可以直接使用具体类型，不要求所有调用都经过接口，也不为形式统一新增 `port`、`adapter` 或通用 `Capabilities` 层。

### 2.3 目录按职责组织

下列路径以 `backend/internal/` 为根，描述目标职责；文件数量根据实现复杂度确定。

| 目录 | 主要文件或内容 |
| --- | --- |
| `core/session/` | `session.go`、历史读取和模型选择等会话规则 |
| `core/task/` | `task.go`、`queue.go`，分别表达待执行输入和队列行为 |
| `core/coordinator/` | 会话定位、输入接纳、任务调度和活动 Run 控制交接 |
| `core/entry/` | Entry、具体事实载荷及持久化编码、消息与模型请求共用的内容块 |
| `core/timing/` | 通用计时记录与测量能力 |
| `core/agent/run/` | Run 的信息、状态规则、`Execute`、输入与结果接收，以及本次执行的收尾 |
| `core/loop/` | ReAct、模型请求、工具调用和上下文构建的核心流程 |
| `service/session/` | 会话应用用例、配置加载与保存协作 |
| `repository/`、`infra/` | 存储契约、可用对象的加载实现及具体外部能力 |
| `bootstrap/` | 依赖创建与能力绑定 |

会话应用用例位于 `service/session`，核心规则位于 `core/session`。队列类型位于 `core/task`，其进程内实例由 Core Coordinator 按 Session 管理；会话领域对象不因此承担队列调度。

### 2.4 前端目录按功能语义组织

目录按功能语义划分，状态实例和事件订阅按 Session 隔离。会话内使用某项能力，不要求将该能力的实现全部放到 Session 目录。下列路径以 `frontend/src/` 为根，文件按实际复杂度收敛。

| 位置 | 职责 |
| --- | --- |
| `api/events.ts` | 事件类型、通道命名，以及按会话订阅通知 |
| `api/sessions.ts`、`api/tasks.ts` 等 | 调用现有后端入口，按业务对象组织请求 |
| `features/session/SessionPage.tsx` | 装配会话内的 Agent、对话、任务和运行展示 |
| `features/session/sessionStore.ts` | 固定会话作用域的数据容器，保存会话、运行和历史数据并通知界面更新 |
| `features/session/applySessionEvent.ts` | 将通知中的明确信息应用到状态，不推断后端执行规则 |
| `features/session/useSessionData.ts` | 会话加载与关闭，作用域订阅的建立和释放 |
| `features/agent/AgentsPanel.tsx`、`AgentConversation.tsx` | 代理列表、选择状态和对话展示 |
| `features/agent/history/` | 历史分页加载、过期请求处理、缓存策略，以及 Entry 合并等纯函数 |
| `features/agent/output/` | 文本、思考、工具和协作卡片等展示组件 |
| `features/run/streaming.ts` | 按 RunID、TurnID 合并和清理临时输出的纯函数 |
| `features/run/useRunControl.ts` | 将停止指定 Run 等操作交给后端 |
| `features/task/TaskComposer.tsx` | 编辑任务内容并提交 |
| `features/task/useTaskSubmission.ts` | 任务提交请求、提交中状态与错误反馈 |
| `features/task/TaskQueue.tsx`、`useTaskQueue.ts` | 队列展示，以及暂停、恢复和取消待办等操作 |

Agent 信息、Run 控制和任务提交按各自语义命名。子代理的补充指令按具体行为组织，与普通 Task 提交分别表达。会话装配使用 Agent、Run、Task 模块提供的能力；共享数据通过必要参数传入，不让功能模块依赖整个页面状态对象。

### 2.5 Provider、上下文与流式资源边界

- `core/provider.Provider` 表达一次协议无关的模型请求尝试。Provider 适配器不负责重试、上下文压缩、工具执行或决定整个 Run 的终态。
- `core/loop` 拥有模型请求的重试策略。首次请求失败后最多重试三次，共最多四次尝试；每次尝试使用新的 `RequestID` 和独立计时，作为独立的 `ModelRequest` 事实保存，`retryCount` 作为请求 Payload 保存。重试仍属于原来的 `TurnID`，累计用量归属同一个 Run。Coordinator 不自动重试整个 Run。
- Provider client 或 `infra/providers/streaming` 持有并释放 HTTP 响应体、解码协程和事件通道。Go 的 `http.Client` 负责 Transport 和连接复用，不替调用方关闭返回的 `Response.Body`。Core 只通过 `Context` 取消请求并消费统一事件，不直接管理协议资源。
- Context 取消应能触发流资源释放并唤醒阻塞读取；资源释放完成由 Provider client 或流式基础设施负责，Core 不因通道关闭而重复释放同一资源。
- `core/context` 负责统一上下文的 token 估算、真实用量校准、压缩准入和压缩后的模型可见内容选择。摘要只在两次 ReAct Turn 之间生成，保存为一个正式 Entry；下一次压缩直接使用最近摘要及其后的新增历史，不保存通用原始 Entry 引用或上下文边界标记。摘要生成完成后即使 Run 被取消也完成保存，保存成功前不使用内存摘要。
- Provider 返回的部分文本、思考内容、工具调用片段、已知用量和计时属于已经发生的请求事实，应随失败或取消的 `ModelRequest` 保存。未完成的部分内容不能自动作为完整 Assistant Entry、可执行工具调用或下一次模型上下文。
- 一次请求必须明确区分正常完成、Provider 或协议错误、Context 取消和无终态关闭；Context 取消或异常关闭恢复时，未完成的 ModelRequest 标记为 `interrupted`。一次请求最多发送一个终态，终态之后不再发送业务事件。

### 2.6 上下文身份、压缩与容量估算

Run 向上下文构建提供本次已经接纳的输入事实。需要跨历史读取定位同一输入时，使用输入 Payload 的稳定消息标识及 Run 归属；指针只用于只读内容共享，不承担持久身份。不能通过 `entry == input`、全文比较或列表下标判断重新解码的 Entry 是否属于当前输入，也不为此给全部 Entry 增加通用 ID 或 ParentID。

同一用户输入在本次模型请求中只出现一次。已在选中的 Entry 中存在时，不再通过独立的 `userPrompt` 拼接。摘要及必要原文的选择按明确语义完成，消息身份和工具配对信息随对应 Payload 表达，不使用 `RetainedEntryIDs` 或通用原文引用列表。

压缩以最近摘要及其后的新增历史为输入。工具交互按 `(RunID, CallID)` 形成完整组，整组摘要或整组选择为原文，不按 Role 的连续长度推定配对完整性。选择原文沿已经确定的历史及声明顺序输出；map 用于定位和集合判断，不决定请求消息顺序。调用方提供已接纳的完整交互，压缩器不另建工具完成状态或在每次编码时重新补回执。

容量估算遵循以下口径：

- 基线使用最近一次成功普通 `ModelRequest` 的真实输入总量，包含缓存读取、缓存写入和未缓存部分；不使用 Run 累计 Usage，也不使用摘要或审核请求作为普通对话的锚点。
- 锚点已经包含的系统提示词、工具定义及协议开销不重复计入；新增内容的结构开销和本次输出预留、必要余量另行计入。
- 只有目标 Provider、协议、模型、系统提示词、工具定义及已选历史仍共享同一前缀时才复用锚点。新增量包括上次响应在本次请求中重放的 Assistant 内容、工具回执及其他新增输入；同一请求重试不重复累加。
- 摘要替换、静态配置、历史选择或临时提示变化导致实际输入不再共享同一前缀时，使旧锚点失效；真实 Usage 缺失或不可用时回退到统一估算。锚点属于当前执行的派生预算数据，基于已有请求事实维护，不新增独立持久化校准体系。
- 回退估算区分 ASCII 与非 ASCII，并考虑 JSON、数字、代码和协议结构开销；经验系数不视为精确 tokenizer 或安全上界，保留适当余量。
- 输入预算、工具定义及协议开销、输出预留和余量共同参与容量判断。90% 等阈值只触发压缩评估，不保证剩余内容一定可容纳；必要内容无法容纳时返回明确的容量错误。
- 预算决策由 `core/context` 和执行流程负责；协议适配器提供准确的字段映射与 Usage 归一化。发送前检查沿用同一预算口径，不以另一套整包 JSON 比例估算覆盖已经校准的基线。

### 2.7 工具结果预算与文件输出

工具执行边界在生成正式 ToolResult Entry 前约束输出。单项 UTF-8 字节上限与模型上下文预算分别处理：前者限制内联载荷，后者确保同批结果和下一次请求的必要内容能够共同容纳。

- 本轮全部结果共享可用预算，可用量扣除系统提示词、已选历史、工具定义、协议开销、输出预留及余量。只检查每条结果的固定字节数不足以约束整组大小。
- 预算判断和最终结果组装由所属执行流程串行完成；并行工具不各自按整份剩余预算预留同一空间。
- 超限输出通过已有文件输出能力完整转存系统临时目录。最终回执返回路径、大小及必要说明，Agent 使用 `read_file` 按 offset 和 limit 读取；返回说明本身也计入预算。
- 若提供头尾预览，预览受相同预算约束，完整原文仍保存到文件。不截断 CallID、参数 JSON 或结果 JSON，也不删除某个调用的回执来满足容量。
- 转存保留结果的错误和副作用语义。转存失败生成明确错误，不将已经执行的操作描述为未执行，不重新运行工具补回输出。
- 文件操作由 Infra 实现，预算和结果接纳归 Core 的执行流程；不把模型窗口规则放入每个具体工具，也不增加长期文件管理实体。

### 2.8 协议编码与请求前缀

ContextBuilder 提供统一、有序且配对完整的模型内容，适配器按各协议映射：

| 协议 | 工具交互编码 |
| --- | --- |
| OpenAI Chat Completions | Assistant 的 `tool_calls` 与按 CallID 对应的 `role=tool` 消息 |
| OpenAI Responses | `function_call` 与对应的 `function_call_output` items |
| Anthropic Messages | Assistant 的 `tool_use` 后紧跟单条 user 消息，其中包含全部对应的 `tool_result`，结果块先于其他文本 |

Anthropic 编码器将批量工具结果编码为同一条 user 消息，并合并紧邻的用户文本；不能只依赖内部 Entry 的一对一消息映射。配对完整性在执行接纳和加载边界保证，适配器不追加持久化事实或重放工具。

摘要、静态请求配置和已有消息未变时，后续请求保持既有前缀稳定。工具定义按确定顺序编码，调用标识映射稳定；序列化不把内部 Entry 时间戳、每次新建的 RequestID 或随机分隔符注入消息正文。

动态预算提醒在本次请求末尾以协议允许的临时消息或文本块传递，不追加到 SystemPrompt，不写入历史，也不进入摘要输入。存在工具交互时，先编码完整工具结果，再附加提醒；Anthropic 合并后的 user 内容仍满足结果在前的规则。缓存路由 key 使用已有会话身份，不以变化的请求身份或摘要文本代替。

## 3. Session 与执行资源的所有权

### 3.1 Session 属于 Core

Session 的持久身份、主 Agent 身份、当前模型选择和连续历史属于核心模型。多个 Run 依次追加到同一主历史，子代理的独立历史关联所属父 Run。

历史顺序由各自日志的追加位置确定，不为 Entry 定义通用的 `ParentID`，也不要求每条执行事实具有独立的历史节点 ID。请求、工具调用、报告和消息等确有引用需要的标识放入对应 Payload；Session 和所属 Run 的存储归属由绑定提交入口及必要存储元数据保留。

Service 通过 Core 取得会话，调用核心规则，并协调必要保存和通知。涉及活动执行的关闭或删除操作，先通过 Coordinator 完成停止与等待。多个 Service 入口不分别维护会话集合、活动执行状态或另一份历史顺序。

### 3.2 持久化数据与进程资源分别表达

| 内容 | 所有权 |
| --- | --- |
| Session 身份、主 Agent 身份和连续历史 | 核心会话模型 |
| 当前模型选择 | Session 领域模型，按架构共识持久化 |
| 已加载 Session 的唯一定位索引 | Core Coordinator 内的 `sessionRegistry` |
| 已加载只读配置引用 | Core 协调范围内按 Session 保存，由配置用例提供和更新 |
| Task Queue、主动暂停 | 队列封装对应行为，Core Coordinator 按 Session 管理实例并协调调度 |
| 模型失效造成的启动阻塞 | Core Coordinator 的调度准入边界，与主动暂停分别表达 |
| 当前 Main Run 的占用与调度 | Core Coordinator 按 Session 维护 |
| Run 身份、配置、状态、执行结果、时间和统计 | Run 统一维护，持久化事实通过 Entry 表达 |
| 单次执行的取消、完成信号、审批唤醒 | 该次 `activeRun` 等明确的控制对象 |
| 运行中输入、子代理结果接收和等待 | 所属 Run 的明确接收与控制边界 |
| Subagent 执行句柄与取消收尾 | 创建它们的具体父 Run |
| Subagent 并发名额 | Core Coordinator 按 Session 协调预留和释放，收尾完成后释放 |

区分持久化与运行状态，不等于必须各建一套同形模型。`context`、锁、channel 是资源和并发实现手段，不能仅凭使用这些类型就决定包归属；它们不进入持久化记录，具体放置位置由职责、生命周期和依赖方向决定。

队列与配置引用的生命周期不依赖前端当前显示哪个 Session。切换查看对象只改变视图，后台 Session 继续执行。关闭 Session 时，Core Coordinator 协调其全部活动执行收尾，再释放登记和相应调度资源。

### 3.3 配置引用

已加载配置按只读引用共享，Core 协调范围内按 Session 定位当前使用的引用。Run 启动时取得本次使用的引用，后续 Turn 保持稳定。Task 只保存待执行输入，不冻结另一份配置。不同 Session 使用独立模型选择，不要求复制整份配置目录和凭据。

配置文件是模型目录、Provider 凭据、工具启停和审批默认值的唯一编辑来源。用户通过当前 Session 的 `/reload` 命令显式加载配置。Reload 只允许在目标 Session 没有活动 Run 时执行；开始后禁止用户输入和新 Task 入队，并清理未领取的待办。成功后目标 Session 使用新的只读内存快照，其他 Session 保持旧引用，已冻结 Run 不受影响。Reload 失败保留原配置引用，不发布成功的配置变更通知。

## 4. Coordinator、会话加载与调度边界

### 4.1 Coordinator 属于 Core

Coordinator 位于 `core/coordinator`，集中实现会话定位、输入路由、同一 Session 内 Main Run 串行执行及队列交接等核心规则。它按 `SessionID` 和具体 `RunID` 定位目标，调用队列、Run 和装配时提供的能力完成协调。

职责分配：

- Coordinator：统一已加载会话入口，接纳消息与调度命令，管理按 Session 隔离的队列和当前 Main Run 占用，协调停止与关闭。
- TaskQueue：维护 FIFO、领取、取消待办、主动暂停和恢复等队列行为。
- 活动 Run 控制对象：持有一次执行的 Run 引用、取消资源、就绪与完成信号等控制资源。
- Run：统一维护本次执行的信息和状态，准备执行，直接调用 Loop，完成必要收尾与终态提交。
- Session 和 Run 核心对象：维护所属领域规则、状态推进和领域事实。
- 父 Run：拥有其创建的子执行句柄、结果接收和收尾边界。

Coordinator 可以持有上述调度资源及引用，但不重复保存 Run 的状态、结果、统计或历史正文。队列和单次执行通过自己的行为入口协作，模型输出处理、工具细节和历史写入不集中到 Coordinator。

### 4.2 已加载会话与 Repo 加载契约

`sessionRegistry` 是 Core Coordinator 的私有索引，放在 `core/coordinator/session_registry.go`，只负责已加载 Session 引用的登记、查找和移除。加载流程位于 `session.go`，不放入 Registry。

Core 对外区分以下语义：

| 入口 | 行为 |
| --- | --- |
| `LoadSession` | 返回已登记的会话；尚未加载时调用加载能力，成功后登记并返回 |
| `GetSession` | 只查找已经加载的会话，不隐式读取存储或触发恢复 |
| `CloseSession` | 协调相关执行停止与完整收尾，再释放会话登记及调度资源 |

Service 通过这些 Core 入口取得和使用会话，不维护另一份会话注册表、注册锁或活动 Session 集合。

Repo 的 Session 加载入口以“成功后返回可用的核心 Session 对象”为契约。具体记录读取、日志重放、内部索引重建和必要恢复由加载实现内部完成；恢复涉及的合法状态和领域规则仍由 Core 维护。Service 和 Coordinator 不显式调用恢复步骤，也不逐条读取历史再组装对象。

可用不要求一次载入全部历史正文。Session 可以具备完整的定位与读取能力，正文继续按需读取。加载失败的对象不发布到 Registry；恢复不自动继续旧 Run、请求模型或重放工具。

Repo 加载方法由 `bootstrap` 绑定给 Core。并发加载、登记和释放在 Core 的明确边界内统一处理，索引锁不覆盖实际存储读取、配置加载或执行等待。

### 4.3 Main Run 与队列的交接

队列按 `SessionID` 定位。调度有两个主要触发入口：

1. Task 入队后，没有当前 Main Run 且队列允许领取时，预留执行位置并启动一项。
2. 当前 Main Run 正常结束并完成必要收尾后，释放占用，再按队列状态决定是否领取下一项。

空闲检查、领取和位置预留具有明确的并发边界。位置从准备阶段开始占用，慢速准备、模型、工具、存储和收尾等待在索引锁外执行。

Run 的 `Execute` 以本次执行及必要收尾为返回边界。正常返回时，Loop、必要的子代理收尾和终态保存已经处理完成；执行或保存失败明确返回错误。Coordinator 通过直接返回或明确完成回调接回控制权，释放本次占用并决定后续调度；Run 不自行领取下一项 Task。中断后的调度遵守明确的队列控制规则，不把中断当作正常完成。

### 4.4 Coordinator 内部按流程拆文件

| 文件 | 主要内容 |
| --- | --- |
| `coordinator.go` | 共享依赖、调度索引及整体关闭入口 |
| `session_registry.go` | 私有 `sessionRegistry` 的登记、查找和移除 |
| `session.go` | 会话加载、获取与关闭的协调入口 |
| `task.go` | 消息和 Task 接纳、待办查询与取消、队列暂停和恢复 |
| `schedule.go` | 调度检查、领取 Task、预留位置及准备下一项 |
| `run.go` | 启动单次执行、接收结束结果和调度交接 |
| `active_run.go` | `activeRun` 及本次执行的控制资源 |
| `control.go` | 定位指定 Run 并提交停止等控制动作 |

文件划分不要求建立同名类型。内部协调行为可以直接作为 Coordinator 的私有方法；状态与资源按实际拥有者封装，不为缩短文件新增纯转发层。

## 5. 命名约定

### 5.1 使用职责名称

“运行时对象”说明对象存在于进程中的生命周期，但不能充分说明职责。领域对象使用已有业务名称，辅助对象使用具体职责名称，不统一附加 `Runtime`、`Execution` 或 `Manager` 后缀。

以下名称表达各自职责，不是必须同时建立的类型清单：

| 名称 | 适用职责 | 使用限制 |
| --- | --- | --- |
| `Session` | 会话的领域模型 | 维护身份、模型选择、连续历史及会话规则 |
| `Coordinator` | Core 中的会话管理与执行调度协调 | 通过核心行为和绑定能力协作，不集中实现全部业务细节 |
| `Run` | 一次执行的身份、配置、状态、结果、统计、执行证据及行为 | 作为唯一核心执行实体，通过 `Execute` 调用 Loop；持久化使用 Entry，控制资源由明确拥有者持有 |
| `TaskQueue` | FIFO 待办、领取与队列控制 | 不表示 Run 的执行状态或自行推进执行 |
| `sessionRegistry` | 已加载 Session 的定位索引 | 归 Core，仅维护登记引用，不展开加载、恢复或执行流程 |
| `activeRun` | 从准备占用到完整收尾的一次活动执行控制 | 可以在 Run 尚未准备完成时存在；状态和结果仍由 Run 维护 |
| `SessionBinding` | 外部调用与目标 Session 的必要绑定关系 | 不持有队列、配置或执行资源的生命周期；已有 SessionID 足以定位时不新增绑定对象 |
| `RunHandle` | 外部只需停止、等待或定位执行时的窄句柄 | 不另持有一份执行状态；不强制设计为接口 |
| `childRuns` | 父 Run 拥有的子执行集合及其收尾 | 集合复杂度需要封装时再抽取 |
| `SubagentQuota` | Session 范围内的执行名额 | 简单计数可以留在协调边界内部，不额外建立全局服务 |

`Controller` 适合确实存在的控制入口，`Scheduler` 适合独立的调度职责，`State` 适合状态值或投影，`Worker` 适合实际存在的工作执行者。按 Session 隔离队列不要求为每个会话另建控制器或调度器，名称也不应暗示尚未采用的并发模型。

如果某类型确实表达一个完整且清晰的运行环境，`Runtime` 可以保留；不为替换后缀引入更模糊的名称。

### 5.2 业务术语一致

- `Task` 仅表示用户放入队列的待办，不用于命名 Run、执行日志或执行结果。
- `Run` 表示一次完整 Loop，`Turn` 表示其中一次 ReAct 迭代，包含普通模型请求及其触发的审核、工具处理和结果接纳；实际模型调用由 ModelRequest 独立记录。
- 日志、变量、方法与事件使用同一身份语义。Run 及其快照使用 `run`、`record` 或 `snapshot` 等准确名称，不命名为 `task`。
- 日志区分 `run_id` 与 `task_id`，需要关联来源任务时使用 `source_task_id`；字段名与实际记录的身份一致。
- 不因新增类型而建立重复的 Status、Outcome、Reason 或 Failure 模型。
- 方法名表达业务动作；文件名表达职责，不按设计模式补齐空文件。

## 6. 状态推进、并发与取消

### 6.1 状态规则集中维护

Run 的身份、配置、状态、结果、时间和统计直接由 Run 维护，开始、结束、输入接纳和结果处理等行为归属于 Run 自身。Run 状态推进集中在 `core/agent/run` 的明确入口，维护合法转移和结果字段一致性。

封装以业务行为为边界，不仅是字段可见性。需要由 Run 维护一致性的字段保持私有，外部通过 `Execute`、输入接纳和结果处理等明确行为协作，不暴露允许调用方任意改写执行记录的通用修改回调，也不为每个字段建立公开 setter。内部赋值服务于完整行为，查询只暴露所需的只读结果。

持久化保存 Entry 表达的事实，不直接序列化整个 Run。加载实现内部根据事实重建可查询、可使用的 Run，构造历史 Run 不启动执行；只有明确调用 `Execute` 才开始本次运行。Session 引用、执行依赖、取消资源等进程内容不进入 JSONL。

需要持久化的状态变化通过 `AppendEntry` 保存。状态推进由所属核心流程决定，提交入口负责接纳和保存事实；记录接口不另外承担状态推进或通知发布职责。

```text
starting → running → ending → ended
starting / running / ending → ended + interrupted
```

`interrupted` 只作为终态结果，不新增生命周期状态。用户主动停止和异常关闭恢复都得到 `Outcome=interrupted`，FailureCode 分别表达请求取消和恢复收敛。`ending` 只表示正常完成的收尾；`ended` 是所有终态的生命周期状态。`yielded` 表示 Subagent 完成后主动向所属 Main Run 交付结果，不表示通用等待状态。

状态约束在拥有者入口判定，下层内部步骤使用已确定的前置条件，避免应用入口、Run 和内部步骤反复校验同一条件。是否返回错误应取决于该入口是否需要处理真实的状态冲突，不机械给每个内部赋值方法增加错误分支。

既有 Outcome 和 FailureCode 应结合上述状态语义收敛。保留的字段必须表达独立信息，不能要求多个字段分别维护同一个事实。

### 6.2 一个 Run 只有一个 Loop 执行者

模型请求、输入消费和后续 Turn 由同一 Run 的执行流程串行推进；同一模型响应中的工具调用按 Provider 返回顺序登记。只读工具可以并行执行；会修改项目文件或其他外部状态的工具按 Provider 顺序串行执行。每个工具结果通过 CallID 配对，并按 Provider 调用顺序组成一个工具结果调用块后追加到历史；完成顺序只影响实时通知，不改变历史顺序。

工具交互以所属 Run 和 CallID 配对；一轮有多个声明时，下一次普通请求前必须取得或补齐全部回执。正常中断由执行流程保留已取得的可靠结果，对未执行或缺少可靠结果的调用补错误回执，再完成本轮结果保存；不把半组结果发布为可继续请求的上下文。

异常关闭后的缺口由会话加载实现根据已保存声明和回执的 CallID 差集补齐，按声明顺序组成可用交互，保存成功后才发布 Session。已有结果不覆盖，缺失结果不自动重放；ContextBuilder 和 Provider 编码器不各自生成虚拟回执。加载和配对沿各日志的追加顺序完成，不引入历史分支或通用父指针。

外部消息、子代理回调通过明确的接收入口提交数据和唤醒信号，不直接并发修改 Loop 上下文，不分别启动新的 Loop。Hook 不得修改已经冻结的工具参数。

已接纳输入与执行完成使用同一个明确的并发边界：完成前处理已接纳的待交付指令，终结后拒绝对子代理继续输入。Main 的普通任务输入遵守业务架构的排队规则：执行中提交的输入进入目标 Session 的后续队列，不注入当前 Run。已接收的排队输入和子代理指令均不能丢弃。

输入用明确的业务类型表达，不建立承载全部业务的通用事件总线。是否共用一个输入结构，以实际消费和持久化语义为依据。

### 6.3 锁与资源靠近拥有者

- Coordinator 的索引锁只保护查找、登记和释放，不包住模型、工具、存储、Hook 或回调调用。
- Task Queue 只存在内存；暂停只阻止领取和启动，不持久化队列事实。
- `/reload`、关闭 Session 或明确清理队列时，只清理尚未领取的待办；已开始的 Run 不属于队列。
- Main Run 以 `completed` 正常结束且队列未暂停时自动启动下一项；主动 `interrupted` 不自动推进后续任务。
- Subagent 名额检查与预留原子完成；取消已接收不等于名额已经释放。
- `Locked` 后缀方法明确注明调用方应持有哪一把锁；不同锁的顺序必须清楚。
- 需要串行提交的历史写入由历史拥有者处理，不借用全局索引锁串行化全部 I/O。
- 外部停止命令定位明确的 RunID，不能在等待后改为停止 Session 的另一条执行。

Context 用于取消、超时和请求范围，不承载业务状态。创建取消资源的执行管理流程负责取消和释放；完成信号必须覆盖必要收尾。子代理完成回调由外层执行流程发起，不依赖已经取消的子执行 Context。

## 7. 单次执行与 Subagent 协作

### 7.1 Main Run 的职责交接

1. 外部消息或调度命令进入 Core Coordinator，定位目标 Session。
2. Coordinator 按业务输入规则接纳消息或入队，并在允许启动时领取 Task、预留 Main Run 位置。
3. 从 Task 创建 Run，固定本次配置并绑定所需能力，由 Run 提交用户输入和初始执行事实。
4. Run 的 `Execute` 直接调用 Loop；Loop 每轮读取已接纳历史，经 ContextBuilder 构建上下文，必要时压缩，再推进模型请求和工具执行，通过同一 `AppendEntry` 提交本轮事实。
5. Run 处理结束原因，并取消、收尾仍活动的子代理。
6. Run 通过 `AppendEntry` 保存本次执行终态，完成必要收尾后返回。
7. Coordinator 接收完成结果，释放占用并按队列状态决定下一项。

Session 管理会话身份、模型选择和连续历史；TaskQueue 封装待办行为；Run 完成本次执行；后续调度由 Core Coordinator 直接推进。Loop 不领取 Task，Coordinator 不逐条处理模型输出或维护 Turn 内部状态。Run 和 Loop 分别发布自身的运行通知，通知与事实提交保持独立。

### 7.2 子代理归属与完成回调

Subagent 严格属于创建它的 Main Run，禁止递归创建 Subagent。原生工具通过已绑定父 Run 的执行能力完成启动和取消；Loop 不需要获得完整 Coordinator。

子代理启动异步返回身份。创建时冻结工具集合、工作目录和审批边界的权限快照；可以使用父 Run 的工作目录和已冻结配置，但不能发起人工审批、风险审核或请求额外权限。未获授权的工具不进入 Provider 工具描述，实际执行边界仍再次检查该快照。

子执行结束并完成必要收尾后，统一完成出口依次完成：

1. 保存子代理结束结果和历史。
2. 将本次结果以 `yielded` 交付给绑定的父 Run 接收对象。
3. 父 Run 保存收到的报告或结束信息，并由主动的等待或收集工具接纳为后续模型输入。
4. 保存成功后唤醒等待；不按 Session 当前 Run 重新查找接收者，也不自动把正文注入 Main Agent 上下文。

完成结果关联子执行身份、ParentRunID 和原始 ParentCallID。父 Run 取消时立即取消其全部子 Run；子 Run 完整收尾前持续占用名额。每个 Session 最多 10 个活动子 Run，不建立额外的 Subagent 等待队列。

### 7.3 原生等待与授权

等待先读取已接收但未消费的报告和结束结果，再使用原生唤醒机制挂起。`any` 在收到新报告或目标全部结束时返回，`all` 等待目标全部结束。两种模式的单次等待上限均由工具入口固定为 30 秒。等待到期返回 `timed_out` 和空报告数组，待领取的报告留给后续调用。父 Run 取消通过 Context 中断等待。

Main Agent 通过明确的等待或收集工具主动获取 Subagent 结果；完成通知只登记结果和唤醒等待，不自动修改 Main Agent 的模型上下文。ReportID 用于正常新增报告消费，MessageID 用于补充指令接纳。等待结果引用已保存的报告，不重复复制报告正文。

委派参数在入口解析和校验一次。授权形成当前 Subagent Run 使用的稳定数据，同时约束 Provider 工具描述与真实工具执行。子代理不拥有人工审批或风险审核权限；实际工具执行仍在冻结的权限边界内检查，不在各模块分别复制另一套权限判断规则。

## 8. 持久化、错误与通知

### 8.1 AppendEntry 是唯一的执行事实提交入口

Loop 和 Run 需要持久保存的执行事实，统一通过 `AppendEntry` 提交。执行事实持久化只暴露这一个业务入口，不设置独立的 Recorder 或按记录类型划分的平行写入入口。具体 JSONL 序列化、文件选择和写入由存储实现完成，调用方不直接操作 JSONL。

| 调用方 | 通过 AppendEntry 提交的事实 |
| --- | --- |
| Loop | Turn 边界、模型请求与响应、模型输出、工具调用与回执、摘要，以及对应的用量和计时 |
| Run | 本次用户输入、Run 的开始和终态、结果、子代理报告及结束结果等执行事实 |

事实使用 `core/entry` 中明确的公共类型表达，消息正文和执行元数据分别表达。ContextBuilder 和历史查询按业务语义选择所需内容，执行元数据不直接作为消息正文交给模型。Run 的状态、请求列表、统计和查询索引基于已接纳的事实维护，不各自形成另一条执行事实写入通道。

Session 主历史或子代理独立历史的归属在执行准备、绑定提交入口时确定，调用方不在每次提交时重新选择主历史或子代理历史。Loop 和 Run 调用同一 `AppendEntry` 能力，底层按归属和事实类型选择对应日志。Session 确定历史范围与追加顺序，Run 使用已接纳的只读 Entry 引用记录执行证据。

事实的准入判断由接纳边界统一完成。Run、Loop 和上下文构建消费已经接纳的只读 Entry 时，不重复比较完整正文或重新校验同一归属。维护执行证据和派生索引不构成另一轮准入，也不形成另一条写入通道；新的运行状态变化和真实权限使用仍由相应拥有者判定。

`AppendEntry` 保留明确的同步结果和错误，执行流程能够知道是否保存成功。一次事实只提交一次；正常执行和加载恢复使用同一事实语义，不重复持久化同一份内容或统计。

### 8.2 记录与通知分别调用

执行流程分别调用 `AppendEntry` 和 Emitter，并在明确位置调用记录相关的观察 Hook。`AppendEntry` 负责事实接纳和同步保存，Run 维护已接纳事实的只读执行证据，Emitter 负责发布执行过程中发生的变化；提交入口不隐式发布 UI 通知或调用观察 Hook，通知订阅者不承担记录或执行推进职责。

提交结果、执行证据接纳和通知发布具有明确的调用关系，执行流程依据各自结果继续处理，不将这些职责全部隐藏在通用条目追加包装函数中。职责分开不要求新增纯转发层或独立管理对象。

Turn 开始和结束等运行通知由 Loop 的明确执行出口发布，依据实际执行结果，与持久化调用解耦。模型文本增量、工具进度等实时通知可以直接发布，完整内容形成 Entry 后再保存，不逐 Token 写入 JSONL。

运行结束通知表达执行结果，保存成功通知依据保存结果。前端收到运行结束通知不等于相关历史已经保存成功，不能用通知替代提交结果。

持久化事实、内存已接纳结果和 UI 展示状态分别表达。写入失败不能显示为已成功保存，也不能因为内存还保留内容就继续正常执行。已经发生的文件修改或工具副作用不因日志失败重放。

报告和完成结果通过 `AppendEntry` 保存成功后，才能作为新增输入交付或唤醒等待；子代理完成结果使用 `yielded` 语义主动交付给绑定的 Main Run。结果交付和等待唤醒属于明确的业务调用；核心提交、取消和调度不依赖可选 Hook 或 UI 事件订阅者。

子代理与父 Run 的两侧日志不构成原子事务。真实写入错误应明确上报并停止相关执行，不增加回调自动重投、恢复队列或可靠消息投递协议。

### 8.3 错误和重试

- 使用结构化错误和原因，按错误类型处理，不依赖错误字符串。
- 在负责业务语义的边界把错误映射为 Run 结果、前端通知、现有接口返回或日志；避免逐层复制同形错误模型。
- Provider 只负责一次模型请求尝试，不在适配器内部重试或改变 Run 状态。
- 模型请求首次失败后最多重试三次，共最多四次尝试；每次尝试使用新的 RequestID、独立计时和独立 ModelRequest 事实，复用原 TurnID，并保存 `retryCount` Payload。
- 风险审核请求有触发工具调用所在的 TurnID，允许按同一上限重试；达到上限后报告风险审核失败，不降级为人工审批。
- 每次尝试的失败、部分输出、已知用量和重试进度均按实际事实保存并通知；累计用量归属同一个 Run。
- 工具授权模式中，`deny` 是配置或工具策略产生的默认拒绝；`ask`、`auto`、`yolo` 是用户可选模式。人工拒绝保存为工具回执；审核等待投影为 `waiting`，不是 Run 终态。
- 工具参数在执行边界冻结后，Hook 只能观察、记录或阻止，不得修改参数。
- 业务工具错误交给 Agent 决定后续动作，工具自身已有重试可保留。
- Subagent 停止不直接导致 Main Run 失败，是否重新委派由 Main Agent 决定。
- Coordinator 不自动重试整个 Run，不因为保存失败重放工具。
- 子代理正常完成以 `yielded` 结果主动交付。子 Run 中断时交付状态、原因及已收到的部分输出。

### 8.4 前端边界

业务事件使用 RunID 和具体 Payload 表达通知，种类由 Payload 决定。队列等 Session 级事件不要求 RunID。事件定义只使用公共数据类型，发布者自行提供身份与结果，不由公共事件包读取完整 Run 对象。

SessionID 在发布函数与订阅通道上绑定。Coordinator 取得对应 Session 的发布函数，Run 再绑定自身 RunID，并将同一通知能力交给 Loop。Run 和 Loop 发布具体变化时，不反复组装完整归属信息。

Emitter 保持共享的进程内分发能力。其与 Wails 适配层之间保留选择通道所需的会话路由信息；作用域绑定使用函数即可，不要求为每个 Session 创建独立 Emitter 或运行管理对象。

| 通知范围 | 通道 |
| --- | --- |
| Session 内的 Run、工具、历史、配置和队列变化 | `praxis:session:<sessionId>` |

Wails 根据作用域选择通道，统一传递 `kind`、可选的 `runId` 和 `data`。SessionID 由通道表达；事件载荷承担前端所需的数据传递职责，不另建同形的 Run 展示或查询模型，也不按事件种类逐个复制同形的传输类型。必要的展示字段筛选在明确边界完成，内部配置、控制资源和非展示内容不直接传给前端。

运行内定位信息按事件需要保留。例如 Run 开始时提供 Agent 关联和开始信息，后续 Run 事件通过 RunID 定位；Turn 事件和按轮次展示的文本增量保留 TurnID，模型请求保留 RequestID，工具调用保留 CallID。Agent 和父子 Run 的关联在初始化或创建通知中提供，不要求所有通知重复携带。页面写入绑定不作为运行通知的定位维度。

事件类型按实际作用域约束定位字段，而不是给所有事件套用相同的可选字段集合：

| 事件语义 | 类型约束 |
| --- | --- |
| Session 级变化 | SessionID 由通道绑定，不要求 RunID，不用空 RunID 补齐统一来源结构 |
| Run 级变化 | RunID 必填；没有所属 Turn 的事件不强加 TurnID |
| 按 Turn 定位的变化 | RunID 和 TurnID 必填，消费端不以空字符串替代缺失的 TurnID |

上述约束落实在现有 `kind` 判别联合及对应载荷类型中，消费端缩窄事件种类后直接取得所需字段。模型请求和工具调用的定位字段同样按语义声明，不把确实必需的身份统一声明为可选，也不因此复制一套事件模型或增加内部重复运行时校验。

首次打开或刷新时，前端先绑定作用域订阅，再取得并接纳当前完整状态，保留加载期间已经收到的新变化。初始状态可复用现有加载响应或使用初始化事件，具体初始化载荷、合并边界和事件清单按实际语义继续收敛。

过期响应不能覆盖新的查询结果；后台 Session 的有效事件仍更新其所属状态。前端不根据零散布尔事件重新实现后端 Run 状态机、队列调度或 Reload 规则。

对外只传递接口和事件所需的数据，不直接暴露包含内部依赖及控制资源的完整 Run。Wails 使用独立 DTO 和投影函数，不让内部 RunRecord、凭据、取消句柄或推理续传状态直接穿过边界。API 层负责 wire 类型转换、响应形状校验和稳定错误码映射；`null` 表示明确不存在，空数组表示空集合，不使用空字符串同时表达缺失和真实为空。生成的 Wails 绑定通过工具重新生成，不手工修改。

### 8.5 前端 Store 与展示职责

每个已加载 Session 持有固定作用域的 sessionStore，保存会话信息及其所需的执行和历史展示数据。切换会话选择展示哪个 Store，不重置或复用另一个会话的状态容器。

| 数据 | sessionStore 中的职责 |
| --- | --- |
| Agent 信息 | 身份、名称、顺序和所关联的 RunID |
| Run 展示信息 | 接纳后端明确给出的状态和结果，按 RunID 组织 |
| 流式缓冲 | 按 RunID、TurnID 保存当前临时输出，与普通数据分别通知订阅者 |
| 已加载历史 | 按 Agent 保存所需 Entry、分页位置、历史加载状态和错误 |
| 界面选择 | 保存共享展示所需的轻量选择状态，不影响后台执行资格 |

Store 负责保存、读取和变更通知，事件处理函数负责接纳事件数据，Hook 组织异步请求、用户操作和缓存保留策略，组件读取并展示数据。辅助模块可以是纯函数，不为 Agent、Run、历史和流式输出各建立独立的 Store 或订阅管理层。

选择 Agent、接纳历史分页和释放缓存使用明确动作。Run 结束与正文 Entry 接纳分别处理，流式内容何时被正式正文替代、历史缓存保留范围和临时缓冲释放条件使用明确策略收敛，不在多个入口分散维护。

运行状态以后端明确给出的 Run 状态和结果为依据。停止请求只更新操作反馈，不直接将 Run 或 Agent 标记为已中断；最终中断由 Run 状态通知确定。`yielded` 只表示 Subagent 已完成并主动交付，不表示 Main Agent 或界面处于通用等待状态。Turn 开始和结束只接纳对应轮次事实，不据此推导 Run 或 Agent 的执行状态，也不覆盖已接纳的 Run 终态。

流式展示可以筛选普通迭代请求，但统一接收入口不因展示筛选而丢弃摘要、审核等模型请求和用量变化。

订阅跟随已加载会话的数据生命周期管理，当前页面只选择展示对象。后台会话继续更新必要的运行、队列和用量信息；历史正文按需读取。会话用量接纳所属 Run 的更新，不依赖当前可见 Agent 或历史页。

### 8.6 前端操作 Hook 的接口与状态

任务提交、运行控制等操作 Hook 接收完成自身职责所需的业务参数，拥有对应请求的进行中状态、结果和错误，对外返回明确的业务动作及状态。例如任务提交 Hook 提供提交动作、提交中状态、提交结果与错误，页面负责组合展示。

- 页面需要统一禁用或汇总反馈时，从各操作 Hook 的状态派生，不让多个操作共享写入同一组页面 `busy`、错误及错误码 setter。
- 请求代次和过期响应检查由发起请求、拥有相应异步状态的 Hook 维护，不将页面内部请求 ref 作为跨 Hook 控制资源传递。
- 跨 Hook 协作通过必要身份与含义明确的回调完成；操作不依赖整个页面状态对象或内部集合的 setter。
- 接口收敛不引入通用命令框架，不为每项操作另建 Store 或订阅管理层。

## 9. 函数、类型和注释风格

- 主函数按正常业务顺序展开，校验、锁操作和复杂细节放在命名清楚的内部函数中。
- 多步骤闭包逐步换行，复杂对象和较长参数列表按语义分行；不将多个业务步骤挤在同一行。换行优先改善局部阅读，不据此机械创建参数对象或辅助类型。
- 只有复用、封装复杂逻辑或表达明确概念时才抽取函数；不为压缩行数增加转发层，也不为满足固定文件或函数行数上限拆分职责。
- 外部数据在相应入口校验，内部传递已确定类型的值，不反复检查同一输入。
- 运行中的状态变化和权限使用在拥有者边界处理，不与重复参数校验混为一谈。
- 类型归属于拥有其语义和生命周期的位置；正常跨模块引用无需通过复制模型消除。
- 前端目录按任务、运行、代理和历史等业务语义命名；Session 作用域用于创建数据实例和绑定订阅，不作为收纳全部相关实现的目录模板。
- 配置按只读引用共享，短期执行数据不随意存入长期共享服务。
- 指针表达内存共享，稳定消息或调用标识表达跨读取身份；涉及重新解码的对象不通过地址相等判断业务身份，集合匹配也不通过全文比较替代已有标识。
- 不为假设的罕见竞态增加复杂恢复体系；发现真实错误先修复产生错误的位置。
- 注释和项目文档使用中文，Praxis 自身错误信息遵守后端约定使用英文。
- 注释解释并发前提、生命周期、失败后状态等不明显约束，不重复代码字面含义。
- Go 复合字面量的多字段换行、React 写法和生成文件处理遵守各目录 AGENTS.md。

## 10. 实施收敛、风险与验证

### 10.1 实施顺序

1. 根据真实调用梳理每个字段、规则和资源的拥有者，明确 Core、Service 和存储实现的依赖方向。
2. 将 Coordinator 和唯一的 `sessionRegistry` 收敛到 Core；Service 通过 Core 加载和取得会话。
3. 明确 Repo 加载成功即返回可用 Session 的契约，将内部记录读取、重建和恢复封装在加载实现内。
4. 将 Task 和队列行为组织到 `core/task`，由 Coordinator 按 Session 管理队列和 Main Run 占用。
5. 将共享事实和通用计时放到 `core/entry`、`core/timing`，确保公共模块不反向依赖 Run 或 Loop。
6. 将本次执行的信息和行为统一到 Run，由 `Run.Execute` 直接调用 Loop，明确 Run 收尾与 Coordinator 后续调度的交接边界。
7. 将 Loop 和 Run 的执行事实提交收敛到唯一的 `AppendEntry`，统一 Turn、模型请求、用量、计时和 Run 终态的保存语义，分别组织记录与通知调用。
8. 将通知作用域绑定到发布函数与前端通道，前端按 Session 持有固定作用域 Store，按业务语义组织任务提交、运行控制、历史和流式处理模块。
9. 核对完成回调、输入接纳、历史提交、配置更新、前端初始化及队列调度的直接调用关系，再按实际复杂度拆分文件。

`activeRun`、窄句柄和子执行集合按实际需要使用；目录和文件划分服务于明确的状态、资源及调用边界，不要求建立完整的对象层级。

### 10.2 风险与回滚边界

主要风险是拆分后出现重复会话登记或执行状态、取消链路断开、回调投递给错误 Run，或会话及调度资源在收尾完成前释放。通过唯一的 Core 会话注册表、明确单一所有者、固定父 Run 接收对象和完整收尾边界控制这些问题。

按职责小步修改，避免同时重命名全部目录和改写整个执行流程。代码回滚以独立变更为单位，不通过重放已产生副作用的任务恢复状态。涉及持久化格式的实施需说明格式影响；不额外承诺旧数据迁移或旧执行自动恢复。

### 10.3 验证方式

文档核对以 architecture.md 的业务边界、本文的类型所有权和命名一致性为主，结合 current.md 追踪尚未落实的实现。

后续代码实施遵守仓库验证流程：

- 后端在 `backend/` 执行 `go build ./...`、`go vet ./...`、`go list ./...`。
- 修改 Wails 签名后重新生成绑定，并在前端执行 `npm run check`。
